# 능동형 제조 AI 플랫폼 기획서 v4.4 공개 편집본

> 원본 v4.4의 팀 리뷰, 데이터 제약과 검증 절차를 반영한 공개 기획서입니다. 공개 편집일: 2026-10-25. 본문은 설계 및 수용 기준이며 실제 생산라인 운영 결과가 아닙니다.
>
> [전체 변경 기록](README.md) | [이전 v4.3](v4.3-public.md) | [다음 v4.5](v4.5-public.md)

## 1. 개정의 질문

이상 감지와 조치 지원을 연결하더라도, 잘못된 근거를 보여주거나 AI 분석 때문에 대응이 늦어지면 사용자가 판단하기 어렵습니다. 팀 리뷰에서는 정보의 역할과 처리 순서, 데이터로 증명할 수 있는 범위를 다시 정리했습니다.

이 버전이 해결하려 한 문제는 세 가지입니다.

1. 모델의 설명과 통계 규칙의 판정이 섞여 근거를 오해할 수 있음
2. 즉시 처리할 상태와 시간이 필요한 AI 분석이 한 흐름에 묶임
3. 정비 후 정상 여부 확인과 모델 재학습이 구분되지 않음

## 2. 핵심 결정

| 검토한 문제 | 결정 | 기획상 의미 |
|---|---|---|
| 통계 위반을 모델 설명 순위에 강제로 반영하는 구상 | 모델의 기여 인자와 통계 플래그를 독립적으로 제시 | 모델이 실제로 설명한 내용과 다른 분석 사실을 혼동하지 않음 |
| 통계 판정과 AI 원인 분석의 역할 혼재 | 통계는 판정과 기록, AI는 원인 후보와 근거 수집 | 추론을 확인된 사실처럼 제시하지 않음 |
| 긴 AI 처리에 모든 동작을 연결 | 신속한 규칙 처리와 비동기 AI 분석을 분리 | 필요한 초기 동작이 생성형 분석 완료를 기다리지 않음 |
| 보유하지 않은 물리 계측값까지 예측한다고 읽히는 명칭 | 보유 품질 지표의 대리 예측으로 설명 범위를 제한 | 데이터가 증명하지 못하는 제품 기능을 주장하지 않음 |
| 모든 재학습을 같은 흐름으로 설명 | 예측 모델 갱신과 정비 후 이상 감지 모델 갱신을 구분 | 갱신 조건과 승인 주체를 명확히 함 |

알고리즘 자체의 고도화만이 아니라, 사용자에게 어떤 정보가 사실이고 무엇이 추론인지 구분해 전달하는 요구사항 변경입니다.

## 3. 정비 후 검증 흐름

정비가 끝났다는 사실만으로 정상 운영 복귀나 모델 갱신을 확정하지 않습니다. 검증용 웨이퍼의 관측 결과를 기존 분석 흐름으로 처리하고, 엔지니어가 검토할 요약을 제시하도록 설계했습니다.

정상 여부를 확인한 뒤 승인에 따라 이상 감지 모델과 관리 기준을 갱신하는 흐름을 분리했습니다. 예측 모델의 재학습은 데이터 확보와 평가 조건을 따르는 별도 흐름입니다. 재학습 실행과 새 모델 배포도 같은 결정으로 취급하지 않습니다.

이때 물리적 정비와 계측은 시뮬레이터에서 모사합니다. 실제 장비를 복구하거나 실제 계측 장비를 대체했다는 의미가 아닙니다.

## 4. 화면과 판단 재료

| 사용자에게 필요한 것 | 화면 및 정보 요구 |
|---|---|
| 무엇이 감지됐는지 이해 | 통계적 이상과 모델 신호를 구분해 표시 |
| 조치 후보를 비교 | 기준선 조정안과 정비안의 근거를 함께 제시 |
| 왜 추천했는지 확인 | 모델 설명, 비교 상태와 관련 사례를 구분 |
| 그대로 승인할 수 없는 경우 대응 | 수정 승인과 반려 사유 기록 |
| 정비 뒤 결과 확인 | 검증 요약, 승인 여부와 갱신 상태 확인 |
| 해결 여부와 재발 파악 | 실행 뒤 효과 확인과 사건 재개 상태 표시 |

모든 대안이 동등하게 옳다는 뜻은 아닙니다. 추천 순위를 제시하더라도 대안과 근거를 숨기지 않고, 엔지니어가 최종 선택할 수 있는 구조를 의도했습니다.

## 5. 검증 설계

시뮬레이터에 주입한 상황과 시스템이 내린 판정을 분리해 비교하는 채점 구조를 정의했습니다. 정상 복귀 시나리오뿐 아니라 정비 후에도 이상이 남는 상황을 포함해 오탐과 미탐을 확인하려는 계획입니다.

| 평가 질문 | 확인 방법 |
|---|---|
| 서로 다른 근거가 섞이지 않는가? | 모델 설명과 통계 결과가 독립적으로 제시되는지 확인 |
| 정비가 실패한 상황을 통과시키지 않는가? | 주입한 정답 상황과 검증 결과를 비교 |
| 승인 없이 갱신돼서는 안 되는 상태가 있는가? | 승인 전후 상태와 갱신 결과를 대조 |
| 같은 사건을 반복 승인하도록 만들지 않는가? | 중복 알람 및 요청 시나리오 확인 |
| 조치가 실제로 효과를 보였는가? | 실행 후 관찰 상태와 종료 조건을 확인 |

목표 지표와 시뮬레이션 평가 결과는 구분합니다. 원문의 기대 개선율은 기대효과 절에 유지하고, 예시 데이터는 실제 프로젝트 성과로 옮기지 않았습니다.

## 6. 범위의 선택

우선 검증할 흐름은 이상 발생 후 근거와 조치를 검토하는 과정, 그리고 정비 후 검증과 승인에 따른 갱신 과정으로 정리했습니다. 일부 모델 재학습은 동작을 설계하되 해당 시연의 범위와 구분했습니다.

추가 모델과 복잡한 다변량 분석, 알림 연동과 세분된 권한, 에이전트 물리 분리는 확장 후보로 두었습니다. React 기반 관제 화면과 분리된 상태 표시를 통해 사용자 흐름을 확인하는 방향을 반영했습니다. 기능 수보다 연결된 흐름과 검증 가능성을 기준으로 범위를 정했습니다.

이 버전에도 레시피 보정 제외에 관한 이전 해석이 남아 있습니다. 최종 결론으로 사용하지 않고 v4.5의 정정을 함께 확인해야 합니다.

## 7. 개발 전달과 남긴 질문

기획 변경은 모델, 통계 분석, 검색과 화면의 계약에도 영향을 줍니다. 기획 문서에는 각 파트가 제공할 사실과 추론, 필요한 승인 상태와 오류 시 동작을 구분했습니다. 상세 API 및 데이터 구조는 별도 계약에서 다루고 공개본에서는 제외했습니다.

모델 갱신의 구체적 시점, 평가용 데이터 확보, 기준 변화와 장비 이상의 구분은 열린 질문으로 남겼습니다. '미정'인 항목과 이미 합의한 원칙을 구분함으로써 병렬 개발 중 서로 다른 전제가 고정되는 일을 방지하려는 구조입니다.

## 8. 정량적 기대효과와 검증 계획

사업적 기대효과와 평가 목표를 공개본에서도 유지합니다. 실제 프로젝트에서 모두 달성했다는 의미는 아닙니다.

| 항목 | 근거 및 목표 |
|---|---|
| 불필요한 확인 부담 | 서울대 논문의 가성 인터락 약 86%라는 보고를 특정 연구의 문제 규모로 인용 |
| 감시와 진단 개선 | IJSRM 논문의 가성알람 40% 이상 감소, 수율 개선과 탐지시간 단축을 외부 사례로 참고 |
| 정비 후 복구 | 기존 기획의 3~5일 대비 검증 및 승인 후 수 시간 이내라는 기대 시나리오 |
| 사례 검색과 요약 | 30분에서 1분 이내라는 처리시간 목표 |
| 조치 후 평가 | 가성알람 35% 이상 감소와 미탐 0건을 시뮬레이션 수용 기준으로 설정 |

주입한 정답과 시스템 판정의 비교로 실제 달성을 확인하는 계획과, 외부 연구가 보고한 결과는 별도입니다. [출처 및 조건 대조](evidence-review-2026-10-25.md)에 원문의 경쟁 비교와 수치 근거를 함께 보존했습니다.
