# 능동형 제조 AI 플랫폼 기획서 v4.3 공개 편집본

> 원본 v4.3의 현업 피드백 반영과 운영 흐름 재설계를 보존한 공개 기획서입니다. 공개 편집일: 2026-10-25. 기획 당시의 판단을 기록하며 구현 완료나 현장 적용을 뜻하지 않습니다.
>
> [전체 변경 기록](README.md) | [이전 v4.2](v4.2-public.md) | [다음 v4.4](v4.4-public.md)

## 1. 개정 배경

초기안은 이상 감지 이후 레시피 보정을 중심으로 대응 흐름을 구성했습니다. 현업 멘토 피드백을 검토한 뒤 관리 기준선 조정, 정비와 웨이퍼 처분 등 서로 다른 조치를 지원하도록 범위를 바꿨습니다.

이때 레시피 보정 자체를 제외한 해석은 후속 v4.5에서 정정됩니다. 최종 원칙은 레시피 변경의 전면 금지가 아니라 무승인 자동 적용의 금지입니다. 공개본은 이 과도한 해석을 숨기거나 최종 결론으로 고정하지 않습니다.

## 2. 제품 목표의 구체화

이상 신호를 받은 엔지니어가 다음 질문에 답할 수 있어야 합니다.

- 실제 장비 이상인지, 기존 관리 기준이 달라진 상태를 반영하지 못한 것인지
- 기준선 조정과 정비 중 어떤 조치를 검토해야 하는지
- 어떤 웨이퍼를 확인 대상으로 두어야 하는지
- 왜 해당 조치를 추천하며 반영 후 무엇을 확인해야 하는지

이를 위해 알람과 제안, 승인과 실행, 검증을 이어지는 업무로 정의했습니다. '작은 인프라'는 운영 규모의 선택이며 승인과 예외 처리의 생략을 뜻하지 않는다는 원칙을 추가했습니다.

## 3. 요구사항 변경표

| 이전 구상 또는 문제 | 변경한 요구사항 | 판단 이유 |
|---|---|---|
| 레시피 보정 중심 | 관리 기준선 재설정, 정비와 처분 흐름 포함 | 현업 조치가 하나의 보정으로 환원되지 않음 |
| 알람별 개별 처리 | 관련 알람을 하나의 사건으로 묶음 | 동일 원인에 승인 요청이 반복되는 부담 방지 |
| 승인 또는 거절 중심 | 수정 승인과 사유 기록 포함 | 사용자가 제안을 그대로 수용하지 않는 경우도 지원 |
| 승인 뒤 처리 완료 | 효과 확인과 재발 시 재개 상태 정의 | 승인만으로 문제가 해결됐다고 볼 수 없음 |
| AI 추천만 제공 | 옵션과 근거, 이력을 함께 제공 | 승인 판단과 이후 검토를 지원 |
| 불확실한 판단 | 보수적인 기본 동작과 상위 검토 경로 정의 | 근거가 부족한 상황에서 임의 적용 방지 |

## 4. 사용자 흐름과 사건 관리

사건의 생애주기는 발생, 분석, 승인 대기, 조치, 효과 확인, 종료로 설계했습니다. 효과 확인 중 같은 패턴이 다시 나타나면 이전 기록을 이어 사건을 재개하도록 했습니다.

같은 장비에서 시간상 겹치는 알람은 기존 사건에 병합합니다. 처리 단위를 묶더라도 원래 알람 기록은 남깁니다. 승인 요청은 사건 단위로 관리하며, 새 알람을 받았다고 같은 사건의 승인 요청을 반복 생성하지 않습니다.

승인 큐에는 우선순위와 담당자 지정이라는 운영 요구도 담았습니다. 위험한 사건이 일반 알람에 가려지는 일과 여러 사람이 같은 사건을 중복 확인하는 일을 줄이기 위한 설계입니다. 실제 사용자 부담 감소량을 측정한 성과로 제시하지는 않습니다.

## 5. 근거와 승인 정책

승인용 요약에는 이상 상태, 원인 후보, 대안별 근거와 추천 이유를 담도록 했습니다. 근거는 통계 상태, 모델 설명, 관련 매뉴얼과 과거 사례를 구분해 제시하는 구상입니다.

엔지니어는 제안을 승인하거나 수정하거나 반려할 수 있습니다. 승인 사유와 변경 내용도 다음 검토에 활용할 이력으로 남깁니다. 반려 이력이 쌓이면 곧바로 모델이 좋아진다고 단정하지 않고, 이후 품질 평가에 사용할 자료로 취급합니다.

관리 기준선을 느슨하게 바꿔 실제 이상을 가리는 위험도 따로 정의했습니다. 변경 폭과 사전 평가, 승인 및 되돌림 조건이 필요한 이유입니다. 상세 파라미터와 내부 규칙은 공개본에서 일반화했습니다.

| 우선 구현 | 승인 대기, 중복 처리, 반영 실패 등의 예외 정의 | 정상 시나리오만 있는 시연을 피하기 위함 |
| 확장 후보 | 조치 유형별 세분된 권한 모델, 외부 업무 알림, 에이전트 물리 분리 | 기본 흐름을 먼저 검증하고 확장 |

| 지속 제외 | 승인 없는 물리적 변경과 임의 제어값 적용 | 판단 및 책임 경계 필요 |

## 7. 협업 문서와 검증 계획

기획서는 기능명뿐 아니라 입력 신호, 조치 조건, 사용자 선택과 예외가 무엇인지 설명하는 기준으로 사용했습니다. 구체적인 이벤트와 데이터 계약은 별도 명세로 관리하는 구조였습니다. 공개본에서는 계약의 목적만 설명하며 내부 API, 함수명과 스키마는 옮기지 않았습니다.

팀원 제안을 반영해 승인 상태를 별도 작업 흐름으로 관리하는 구현안을 포함했습니다. 팀원이 맡은 분석과 검색 기능은 이 승인 흐름에 필요한 정보를 제공하도록 연결합니다. PM/PO의 역할은 각 파트가 같은 조치와 상태를 뜻하는지 맞추고 변경 이유를 남기는 것입니다.

평가 항목에는 신호별 동작이 정의돼 있는지, 동일 사건의 중복 승인 요청이 생기는지, 관리 기준선 변경이 실제 이상을 가리지 않는지, 필요한 근거가 제시되는지를 추가했습니다. 성공 기준은 계획이며 본 버전 자체가 시험 통과를 증명하지 않습니다.

후속 버전은 팀 리뷰와 데이터 제약을 반영해 모델 근거, 통계 사실과 AI 추론의 경계를 더 명확히 합니다.

## 8. 기대효과와 측정 기준

기대효과는 제품 기획의 판단 근거로 남기고, 달성 결과와 구분합니다. 원문과 후속 정정 자료를 연결해 읽습니다.

| 항목 | 근거 및 목표 |
|---|---|
| 알람 확인 부담 | 서울대 논문이 보고한 가성 인터락 약 86%를 문제 규모의 근거로 참고 |
| AI 기반 감시 효과 | IJSRM 논문이 보고한 가성알람 40% 이상 감소를 외부 사례로 참고 |
| 늦은 이상 발견의 비용 | KLA의 조건부 비용 예시 약 2,100만 달러를 조기 대응의 사업적 근거로 참고 |
| 검색과 승인 자료 준비 | 30분에서 1분 이내를 기획의 기대 시나리오로 설정 |
| 기준선 변경의 수용 기준 | 시뮬레이션에서 가성알람 35% 이상 감소와 미탐 0건을 목표로 정의 |

문헌의 수치와 프로젝트의 목표를 같은 성과로 합치지 않습니다. [근거 검토](evidence-review-2026-10-25.md)에서 출처, 조건과 기획 당시 경쟁 비교표를 확인할 수 있습니다.
