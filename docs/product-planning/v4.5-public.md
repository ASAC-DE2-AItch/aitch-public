# 능동형 제조 AI 플랫폼 기획서 v4.5 공개 편집본

> 원본 v4.5의 요구사항 재확인, 조치별 책임 경계와 제품 검증 방향을 보존한 공개 기획서입니다. 공개 편집일: 2026-10-25. 버전명은 원문 파일명 기준이며 후속 보충 메모가 섞인 부분은 결정의 의미를 중심으로 정리했습니다.
>
> [전체 변경 기록](README.md) | [이전 v4.4](v4.4-public.md)

## 1. 가장 중요한 정정

v4.3에서 멘토 의견을 레시피 보정 전면 제외로 해석했으나, 다시 확인한 결과 제한해야 할 대상은 **무승인 자동 적용**이었습니다. v4.5에서는 레시피 조정 제안을 사람 승인과 효과 검증을 거치는 서비스 범위로 되돌렸습니다.

초기안에도 사람 승인 구상이 있었으므로, 변경을 '자동 제어를 버리고 처음 승인 기능을 넣었다'고 설명하는 것은 정확하지 않습니다. 변화의 핵심은 조치의 종류, 제외 범위와 검증 책임을 구체화하고 잘못 해석한 요구사항을 정정한 것입니다.

## 2. 제품 방향

AITCH는 이상 신호를 받은 뒤 엔지니어가 원인 후보와 조치 대안을 확인하고 결정하는 과정을 연결하려 합니다. 목표 흐름은 다음과 같습니다.

이상 감지 → 근거 수집 → 조치 후보 비교 → 사람의 승인 또는 수정 및 반려 → 적용 → 효과 확인 → 이력 축적

개별 예측, 통계 분석, RAG 검색과 조치 제안은 상용 또는 연구 사례가 있는 기능입니다. AITCH의 설계 목표는 이 기능들을 승인과 검증 흐름으로 통합하는 것입니다. 경쟁 제품에 해당 기능이 전혀 없다거나 시장 최초라고 주장하지 않습니다.

## 3. 조치 선택과 책임 경계

| 판단할 상황 | 검토할 대응 | 기획상 제한 |
|---|---|---|
| 실제 장비 이상이 의심됨 | 정비 및 확인 대상 웨이퍼의 처분 검토 | 근거와 승인, 이후 검증 필요 |
| 공정 조건의 이탈이 의심됨 | 레시피 조정 제안 | 무승인 자동 반영 금지, 승인 후 시뮬레이션 적용 및 효과 확인 |
| 관리 기준이 현재 정상 상태를 반영하지 못함 | 관리 기준선 재설정안 | 실제 이상을 가리는 변경인지 검토 |
| 어느 가설도 충분히 지지되지 않음 | 추가 공정 검토로 전달 | 근거가 부족한데 임의 조치를 선택하지 않음 |

모델의 출력 오차를 보정하는 일과 장비의 공정 조건을 바꾸는 일도 구분했습니다. 물리적 변경을 수반하지 않는 모델 보정은 제한 범위와 기록을 조건으로 자동화하고, 허용 범위를 넘는 차이는 단순히 덮지 않고 이상 신호로 처리하는 설계입니다.

정기적인 기준 갱신과 이상 대응 중 기준선 변경은 목적과 위험이 달라 같은 승인 정책으로 뭉뚱그리지 않습니다. 원문에 있는 구체적 수식과 적용 한계는 공개본에서 일반화했습니다.

## 4. 사용자 관점의 요구사항

### 근거를 보고 대안을 비교할 수 있어야 함

AI가 추천 한 줄만 제시하지 않고, 조치별 근거와 비교 내용을 승인용 요약으로 보여주도록 했습니다. 모델 설명은 모델이 제시한 내용으로, 통계 상태는 관측 및 판정된 정보로 구분합니다. 검색한 유사 사례가 현재 상황에 그대로 적용된다고 단정하지 않습니다.

### 승인 이후까지 확인할 수 있어야 함

승인, 실행과 효과 확인은 서로 다른 상태입니다. 조정 후 결과가 나아졌는지를 확인하고, 충분하지 않으면 재검토하는 흐름을 둡니다. 조치 성공을 모든 문제가 한 번에 해결된 상태로 가정하지 않는 방향입니다.

### 승인 요청 자체가 업무 부담을 늘리지 않아야 함

관련 알람은 사건 단위로 모으고 진행 중인 사건의 정보로 합칩니다. 개별 알람 기록은 보존합니다. 담당자와 우선순위, 변경 및 반려 이유를 확인할 수 있는 운영 요구를 함께 다룹니다.

## 5. 범위와 선택 근거

| 분류 | 항목 | 이유 |
|---|---|---|
| 우선 구현 | 조치별 근거, 대안 비교, 수정 승인과 결과 확인 | 엔지니어의 판단에 직접 필요 |
| 우선 구현 | 통계적 사실과 AI 추론의 구분 | 잘못된 근거에 의한 판단 방지 |
| 우선 구현 | 모델 보정과 재학습, 배포 평가의 조건 구분 | 데이터 부족이나 이상을 무분별한 갱신으로 가리지 않기 위함 |
| 확장 후보 | 추가 물리 계측 연동 | 제공 데이터만으로 검증할 수 없는 영역 |
| 확장 후보 | 고도화된 권한과 외부 업무 도구 연동 | 핵심 흐름을 우선 검증한 뒤 확대 |
| 제외 | 무승인 레시피 자동 적용, LLM의 임의 제어값 적용 | 승인과 검증 책임이 필요 |
| 제외 | 불필요하게 복잡한 대규모 운영 구조 | 교육 환경의 검증 목적에 맞지 않음 |

추가 데이터가 없는 기능은 설계 가능성과 구현 완료를 구분했습니다. 원문에서 검토 모델과 구성 수가 바뀐 항목은 당시 기획 상태이며, 현재 최종 구현과 혼동하지 않도록 저장소 README를 별도로 참고하도록 했습니다.

## 6. 검증과 성공 지표

| 평가 영역 | 확인할 질문 |
|---|---|
| 예측 품질 | 주어진 데이터에서 기준 모델과 비교한 오차는 어떠한가? |
| 이상 감지 | 정상 변화와 실제 이상을 구분하는가? |
| 근거 품질 | 추천에 필요한 정보가 포함되고 사실과 추론이 구분되는가? |
| 상태 및 계약 | 같은 사건의 중복 요청과 잘못된 상태 전이가 없는가? |
| 승인 정책 | 승인이 필요한 변경이 승인 없이 실행되지 않는가? |
| 조치 효과 | 적용 후 평가 조건을 충족하고 재발 여부를 확인하는가? |
| 재학습과 배포 | 충분한 데이터 및 평가 조건을 통과한 경우에만 갱신되는가? |

시뮬레이터가 주입한 정답 상황과 시스템 판정을 대조하는 평가 구상을 사용합니다. 원문의 기대 개선율이나 승인 화면 예시 수치를 본 프로젝트의 실측 성과로 표시하지 않습니다.

기획서가 구상한 항목 전체가 최종 구현됐다는 보장도 아닙니다. 팀의 이후 시연은 교육 시뮬레이션 및 AWS 환경에서 진행했으며 실제 생산라인의 수율이나 비용 개선을 입증한 것이 아닙니다.

## 7. PM/PO가 남긴 결정과 협업 방식

- 현업 의견에 따른 변경뿐 아니라 그 의견을 잘못 해석한 부분의 정정도 버전 이력으로 남겼습니다.
- 요청과 승인, 처리와 효과 확인의 의미를 기획 문서와 개발 계약에서 맞추는 기준을 세웠습니다.
- 기획의 사용자 흐름을 시뮬레이터와 관제 화면, 승인 처리 및 팀 모듈 통합에 연결했습니다.
- 세부 모듈은 팀원이 분담했으며 전체 서비스는 최종 4인 팀의 결과입니다. 기획, 역할 및 범위 조율과 시스템 통합의 담당을 전체 팀 성과와 구분합니다.

이 공개본에는 내부 API, 데이터 계약과 DB 스키마, 실행 코드와 프롬프트, 공정 데이터와 설정값, 개인 식별정보 및 접속 정보를 포함하지 않았습니다. 제품의 목적과 의사결정, 변경관리 및 수용 기준을 보여주는 자료로 사용합니다.

## 8. 사업적 기대효과와 근거

검증한 문헌 수치와 기획의 기대효과를 복원합니다. 외부 연구 결과, 조건부 비용 추정과 AITCH 평가 목표를 각각 표시합니다.

| 기획 판단에 사용한 항목 | 수치와 의미 |
|---|---|
| 알람 확인 부담 | 서울대 논문에서 보고한 가성 인터락 약 86%. 특정 장비 그룹의 관측 결과 |
| AI-SPC 적용의 참고 사례 | IJSRM 논문은 가성알람 40% 이상 감소, 수율 최대 1.7% 개선과 MTTD 30% 이상 단축을 보고 |
| 조기 발견의 경제적 의미 | KLA 예시는 월 2만5천 장, 수율 손실 25%, 말단 검사 약 30일 지연 조건에서 약 2,100만 달러 손실을 제시 |
| 사례 검색 및 요약 준비 | 30분에서 1분 이내, 30배라는 기대 시나리오 |
| 정비 후 복구 | 기획 기준 3~5일 대비 수 시간 이내의 복구 기대치 |
| 프로젝트 수용 기준 | 가성알람 35% 이상 감소 및 미탐 0건을 시뮬레이션 평가 목표로 정의 |

원문 경쟁 비교표와 현재 공식 기능 확인은 [근거 검토](evidence-review-2026-10-25.md)에서 구분해 제공합니다. 기획 시점의 검증을 없던 일로 처리하지 않고, 현재 제품 설명과의 차이는 별도 기록합니다.
