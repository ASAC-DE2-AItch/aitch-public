## 1. 제품의 목적과 대상

식각 공정의 이상 신호를 발견한 뒤 엔지니어가 원인을 확인하고 조치를 결정하는 과정을 지원합니다. 예측 점수와 알람을 보여주는 것에 그치지 않고, 관련 근거와 조치 후보를 모아 승인 가능한 형태로 전달하는 것이 초기 제품 방향입니다.

주요 사용 상황은 이상 알람 확인, 정비 전후 상태 점검, 유사 사례와 변경 이력 검색, 조치안 검토입니다. 대상은 공정의 상태를 판단하고 조치를 검토하는 엔지니어로 정의했습니다. 사용자 유형은 기획 가설이며 직접 고객 도입을 통해 검증한 페르소나로 표현하지 않습니다.

## 2. 문제를 기능으로 연결한 과정

| 문제 | 사용자에게 필요한 판단 | 초기 기획에 반영한 기능 |
|---|---|---|
| 최종 검사 전에 이상을 파악하기 어려움 | 어떤 웨이퍼와 장비를 먼저 살펴볼 것인가? | 센서 데이터 기반 품질 예측과 조기 경보 |
| 예방정비 뒤 센서 특성이 달라짐 | 장비 이상인가, 예측 모델의 기준 문제인가? | 분포 변화 감지와 모델 갱신 검토 |
| 챔버별 상태와 관련 지식이 분산됨 | 다른 챔버와 어떤 차이가 있고 비슷한 과거 사례는 무엇인가? | 챔버 비교, 관련 사례와 매뉴얼 검색 |
| 조치 제안을 그대로 신뢰하기 어려움 | 왜 이 조치가 필요한가? | 근거 카드와 승인용 요약, 사람의 승인 |

원문은 문헌과 업계 자료로 문제의 규모를 설명했습니다. 공개본은 해당 수치를 기대효과와 근거 절에 보존하고, 출처 및 조건을 연결해 실제 제품이 지원하려는 판단과 함께 설명합니다.

## 3. 초기 서비스 흐름

1. 센서 데이터를 받아 웨이퍼의 품질과 장비 상태를 분석합니다.
2. 통계적 이상과 챔버 간 차이를 확인합니다.
3. 보정 후보를 만들고 관련 사례와 매뉴얼을 검색합니다.
4. 모델 설명, 과거 사례, 위험과 추천 조치를 승인용 요약에 담습니다.
5. 엔지니어가 승인하거나 거절하고 필요하면 제안값을 수정합니다.
6. 승인된 조치의 결과를 확인하고 판단 이력을 축적하는 흐름을 설계합니다.

초기안에도 사람 승인 구상이 있었습니다. 이후 버전에서 추가로 정리한 것은 조치의 종류와 승인 조건, 예외 및 효과 검증의 범위입니다. 위 흐름은 설계 목표이며, 실제 장비의 자동 제어를 구현했다는 의미가 아닙니다.

## 4. 대안 검토와 선택

| 검토 영역 | 선택한 방향 | 선택 이유 또는 제약 |
|---|---|---|
| 예측 모델 | 설명 가능한 기여 인자를 제공하는 모델을 우선 검토 | 숫자와 함께 판단 근거가 필요 |
| 통계 감시와 AI 감시 | 두 접근을 결합하는 구조 | 규칙 기반 이상과 미세한 분포 변화를 함께 검토 |
| 근거 검색 | 과거 사례, 매뉴얼, 변경 이력과 공정 지식을 구분 | 검색 결과가 조치 판단에 연결돼야 함 |
| AI 역할 | 분석과 제안, 승인 자료 생성 | 실제 적용의 판단은 엔지니어에게 남김 |
| 개발 방식 | 데이터와 이벤트 계약을 정하고 모듈을 병렬 개발 | 통합 단계의 해석 차이와 연동 위험 완화 |

상용 솔루션 비교표는 기획 당시 검증한 조사 기록으로 보존합니다. 현재의 공식 기능 설명과 대조한 결과는 별도 근거 검토 문서에 연결했습니다.

## 5. 우선순위와 하지 않기로 한 것

원문의 Must와 Should는 즉시 구현 범위로, Could는 확장 후보로 분리했습니다.

| 구분 | 범위 | 판단 기준 |
|---|---|---|
| 즉시 구현 | 예측과 이상 감지, 챔버 비교, 근거 검색, 승인용 요약, 승인 흐름 | 이상 확인부터 조치 검토까지 연결되는 최소 흐름 |
| 확장 후보 | 추가 예측 모델, 복잡한 다변량 분석, 별도 알림 연동, 에이전트의 물리적 분리 | 설명과 통합, 검증 부담에 비해 초기 효용이 낮거나 추가 근거 필요 |
| 제외 | 실제 장비 레시피의 무승인 자동 적용, LLM의 임의 제어값 생성 | 검증과 책임 경계가 확보되지 않음 |
| 제외 | 과도한 대규모 운영 구조와 연구 수준의 제어 기법 | 교육 기간 안에 흐름을 검증하는 목적과 맞지 않음 |

일부 초안에는 데이터에 없는 물리 계측값을 추정하는 표현과 특정 비교 챔버를 전제한 설계가 남아 있었습니다. 후속 버전에서 데이터를 확인하고 현업 의견을 반영해 정정합니다. 이 초기 문서를 최종 설계처럼 읽지 않도록 구분합니다.

## 6. 실행 계획과 산출물

원문은 약 8주의 실행 계획을 네 단계로 나눴습니다.

| 단계 | 주요 산출물 | 확인하려 한 내용 |
|---|---|---|
| 데이터와 기준 모델 | 데이터 유입, 기초 모델, 저장 구조와 계약 | 입력부터 예측까지 연결되는가? |
| 통계 분석과 장비 비교 | 이상 감지, 비교 지표, 관제 요소 | 이상 신호를 구분하고 확인할 수 있는가? |
| 검색과 AI 분석 | 유사 사례 검색, 근거 카드, 승인용 요약 | 제안의 근거를 설명할 수 있는가? |
| 승인과 통합 시연 | 승인 흐름, 조치 반영과 결과 확인 | 독립 기능이 하나의 사용자 흐름으로 동작하는가? |

PM/PO는 기획과 계약, 역할과 범위를 조율하고 팀원은 분석 및 검색 등의 모듈을 분담하는 구상이었습니다. 원문 API 및 DB 명세는 공개 편집 범위에서 제외했습니다.

## 7. 성공 기준과 위험

원문에서 예측 오차, 감지 속도, 검색 적합성, 승인 요약의 정보 충족도, 전체 처리시간과 시뮬레이션 효과를 성공 기준으로 정의했습니다. 이는 목표와 평가 항목이며 달성 결과가 아닙니다.

주요 위험은 단일 데이터 조건의 일반화 한계, 잘못된 이상 기준, 검색 품질, 모듈 통합 복잡도와 모델 실행 비용입니다. 모델 교체나 규칙 기반 대체, 계약 사전 합의 등 대안을 검토했습니다. 실제 데이터와 합성 시나리오의 평가 범위도 구분해야 합니다.

다음 버전에서는 초기 구상을 현업 절차와 대조하고 조치 범위 및 승인 흐름을 다시 정리합니다.
