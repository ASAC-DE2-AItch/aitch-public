> **작성**: PM 윤준호, 2026-07-19
> **v1.1 (2026-07-20, 멘토 피드백 반영)**: ① 세계관 = **장비 1대(4챔버)** — 구 "베이 1개·6챔버"는 용어·구성 오류 정정 (베이=장비 여러 대의 구역. 4챔버 = 멘토 현장 표준 구성, 시뮬 스펙 v1.3) ② **Nelson 룰 프루닝** 미확정 항목 등재 — 알람 개수 자체 축소 + 룰 수 축소, 실데이터 채점 후 결정 (§6, Q6 개정) ③ 규모 산수 4챔버 재계산 (37,000포인트 · ①~400건 · ②~245건).

> **정본 관계**: 스키마 정본 = `API_Contract_명세서.md` §3, 게이트 값 정본 = `config/params.yaml` (B7 `context_score_agent_min: 31`), 원칙 = 헌법(CLAUDE.md) 1-2·1-4. 이 문서는 **근거 설명서**이며 충돌 시 정본이 우선한다.
> **미확정 표시**: 산식 배점은 **B4-1에서 팀원 B가 확정**한다 (`context_score_pred_weight: null`이 그 증거). 본문 §4 배점표는 이해용 가안(v0)으로 명시 구분.

## 1. 어떤 알람이 하루 수백 건 울리는가 — 판정 우주 산수

### 1-1. 판정 포인트의 규모

| 항목 | 값 | 근거 |
|---|---|---|
| 범위 | **Etch 클러스터 장비 1대 = 챔버(PM) 4개** (실데이터 1챔버에 오프셋+노이즈로 복제) — 멘토 확인 구성 (2026-07-20, 시뮬 스펙 v1.3). ⚠ 용어: 이 단위는 "베이"가 아니라 **장비**다. 베이 = 장비 여러 대의 구역 | 시뮬레이터_스펙 v1.3 §멀티챔버 |
| 처리율 | **231 wafer/일/챔버** | B4-4 정정 실측 (params `rolling_window_n` 주석: N500 ≈ 2일치) |
| 판정 그룹 | [Recipe × Step × 센서 × 윈도우] — 보수적으로 **40그룹/챔버**만 가정 (센서 10종 × 스텝 2 × 윈도우 2. 실제 후보는 스텝 5 × 센서 15+로 더 큼) | 데이터_사전 (Step 5개, 연속 센서 15+) |
| Nelson 룰 | N1~N8 동시 적용 | 팀_RnR B 절 |

→ 판정 포인트 = 231 × 40 = **9,240건/일/챔버**, 4챔버 **약 37,000건/일**. 알람은 이 포인트들 위에서 발생한다. **아래 규모 산수는 전부 장비 1대 기준**이다 — 베이는 이런 장비가 여러 대, 팹은 그런 베이가 수십 개라 전사 규모는 ×수십~수백이 된다.

### 1-2. 오탐(가짜 알람)의 5대 원천 — 각각 실측 규모

**① 확률적 오탐 — 8룰 중첩.** N1(±3σ) 하나만이면 오탐율 0.27%/포인트지만, 감도 룰(N2 추세, N5 2/3존A…)을 전부 켜면 관리도 문헌(Montgomery) 기준 in-control ARL₀가 370→약 92로 줄어든다 = **정상 상태에서도 포인트당 약 1.1%가 위반 판정**. 37,000 포인트 × 1.1% ≈ **하루 ~400건**이 순수 통계 소음으로 발생 가능. *(멘토 피드백 2026-07-19: 룰 셋 축소로 이 원천 자체를 줄이는 방향 검토 — §6)*

**② 구조적 오탐 — 비정규(치우침) 분포.** 우리 실측: **KEEP\* 6그룹(전부 C6_0)은 ±3σ 오탐 4.43%** (B 실측, 2026-07-10 결정 A·B 조합②). 이 6그룹만으로 6 × 231 × 4.43% ≈ 61건/일/챔버, **4챔버(장비 1대) 환산 ~245건/일**. 분포가 한쪽으로 치우친 센서는 ±3σ 대칭선이 꼬리 쪽에서 정상값을 계속 밖으로 밀어낸다.

**③ 과도(transient) 구간 오탐.** Step 4 초기 3샘플(첫 9초, `C42=1`)은 점화 스파이크로 값이 튄다 (예: C11 점화 −1→−335). 윈도우 분리 없이 판정하면 **매 wafer의 점화 순간마다** N1이 걸린다 — wafer당 1건씩이면 이것만 231건/일/챔버.

**④ 기준선 노후 — PM 직후 레짐 이동.** 요란 PM 전환 시 센서 레벨이 이동한다 (실측: C17 계열 **+317 수준 이동**). 관리선을 리베이스하지 않으면 새 정상상태의 **모든 wafer가 위반** — 정착까지 하루 231건 전부가 알람. "고장"이 아니라 "기준선이 낡은 것"인데 알람으로는 구분되지 않는다.

**⑤ 공통원인 동시다발 — 참조 오염.** fleet median 자체가 흔들리면(참조/유틸리티 공통원인) 4챔버가 **동시에** TTTM 이탈 알람을 낸다. 같은 장비의 PM들은 트랜스퍼 모듈·유틸리티를 공유하므로 공통원인이 실제로 잦다. 진짜 문제는 챔버가 아니라 참조인데, 알람은 4배로 증폭된다 (`tttm.reference_suspect` 역방향 룰의 존재 이유).

### 1-3. 결론

②의 실측(4.43%)만으로도 **장비 1대(4챔버)에서 하루 ~245건**, ①~⑤ 합산이면 장비 한 대만으로 수백 건 규모가 구조적으로 나온다 (베이·팹 전체는 ×수십~수백). 그리고 이 중 **진짜 개입이 필요한 사건은 하루 몇 건**이다. 알람 총량을 줄이는 게 아니라 **"사람을 부를 알람"을 고르는 문제** — 이것이 Context Score의 존재 이유다.

## 2. 설계 원칙 — "지우는" 게 아니라 "기록과 개입을 분리"

정확히 하면 Context Score는 알람을 **지우지 않는다**. 전 건이 `spc_violations`에 기록되고 `fdc.alert` 단일 채널(헌법 1-2)로 발행된다. 걸러지는 것은 **사람과 LLM의 호출**이다:

```
[생성 억제]   가한계 Phase 0 (PM 직후~Qual): 알람 발행 자체 억제 — 원천 ④ 대응
              KEEP* 6그룹 분위수 관리선: 오탐 4.43% → 0.30% — 원천 ② 대응 (헌법 1-1 예외 2)
              과도/정착 윈도우 분리 판정 (C42): 점화 스파이크 별도 축 — 원천 ③ 대응
              C6_1 등 baseline 없는 그룹 감시 skip (7/11 팀 확정)
                       │  그래도 발생한 알람 (전 건 기록·발행)
                       ▼
[호출 게이트] Context Score < 31 → 기록만 (LLM 미가동, 대시보드 조회는 가능)
              Context Score ≥ 31 → Agent 가동 (리포트 3종 병렬)
              severity=critical  → 점수 무관 즉시 가동
              엔지니어 수동 요청 → 점수 무관 가동 (trigger_type='manual')
                       │
                       ▼
[병합]        Incident 그룹핑: 같은 챔버+시간창 알람 N건 → Incident 1건 (헌법 1-4)
                       ▼
[통합]        Supervisor: 리포트 3종 → Brief 1장 → 승인 pending 동시 1건
```

엔지니어 접점의 변화: **알람 수백 건/일 → Agent 후보 수십 건 → Incident 몇 건 → 화면의 pending은 Incident당 1건.**

## 3. Context Score 입력 — 확정된 4축

점수는 "이 알람이 **진짜 사건의 맥락** 위에 있는가"를 본다. 단일 룰 위반(1축)이 아니라 **독립 채널들의 수렴**이 점수를 올린다.

| 축 | 소스 | 무엇을 보나 | 상태 |
|---|---|---|---|
| ① Nelson 위반 | B 판정 엔진 (`fdc.raw`) | 룰 종류(단발 N1 vs 추세 N3), 지속성, 위반 크기, 과도/정착 윈도우 | 확정 |
| ② TTTM | B (fleet median + Qual 스냅샷) | 다른 챔버 대비 얼마나 다른가 (warning 2.0 / critical 3.0), `reference_suspect`면 감점 방향 | 확정 |
| ③ AE Drift | A 발행 `fdc.prediction`을 B가 추가 구독 | 다변량 관계가 깨졌는가 (단변량 룰이 못 보는 축) | 확정 (M1 잔여 = 연동) |
| ④ predicted_c65 | A 예측치 | 품질 임계(P95=1404) 방향으로 가는가 — **심각도 가중 항, 단독 발동 불가, 가한계 Phase 0~1 가중 자동 0** | 구조 확정, 가중치 **B4-1 때 B 기입** (`context_score_pred_weight: null`) |

핵심 논리: 원천 ①(통계 소음)은 축 1개만 걸리고, 진짜 사건은 **여러 축이 동시에** 걸린다. "감지 3채널 수렴"(서비스_전체흐름 §브리핑)이 점수의 물리적 의미다.

> ⚠️ 아래 배점은 **동작 이해와 프론트 목업 정합을 위한 PM 가안**이다. 확정 산식·배점은 B4-1에서 B가 정하고 params에 등재한다.

| 항목 | 가점 |
|---|---|
| 룰 기본점 | N1 단발 10 / N2·N4 12 / N3 추세 15 / N5~N8 10~15 |

| 과도 윈도우 | 합산 후 ×0.5 (점화 구간 스파이크 할인) |

## 5. 예시 6종 — 무엇이 걸러지고 무엇이 올라가나

### 예시 1 — 단발 3σ 스파이크 (하루 수백 건의 "대부분")
CH2 · C31(RF Power) · Step 4 과도 구간에서 1점이 +3.1σ. TTTM 정상(0.8), AE 정상, 예측 정상.
**점수(가안)**: 룰 10 + 크기 0.1σ초과 ≈ +1 → 11, 과도 할인 ×0.5 → **≈ 6점 → 기록만.** 축 1개짜리 통계 소음. `spc_violations`에 남고 S2 차트에서 조회는 가능하다.

### 예시 2 — 추세 + 다채널 수렴 (계약 §3 예시 그대로)
CH3 · C11(DC Bias) · N3 "6점 연속 상승" (정착 구간) + TTTM 2.3 (top gap C11 4.1%) + AE drift 상승 + predicted_c65 상승.
**점수(가안)**: 15(N3) + 10(지속) + 15(TTTM≥2) + 15(AE) + 17(pred) = **72 → Agent 가동.** → 리포트 3종 병렬 → Supervisor 4지선다 → Brief. *API 계약 §3의 `context_score: 72` 예시가 이 사례다.*

### 예시 3 — Critical 즉시 우회
UCL을 크게 벗어난 지속 위반, severity=critical. **점수 계산과 무관하게 즉시 Agent 가동** (게이트 3중화 ②). 점수는 "애매한 중간지대"를 거르는 도구지, 명백한 사건을 지연시키는 도구가 아니다.

### 예시 4 — 저점수 + 엔지니어 수동 요청
score 18로 게이트 미달인데, 엔지니어가 경험상 냄새가 난다고 판단 → S3 Incident 행의 **"AI 분석 요청"** 클릭 (`POST /incidents/{id}/analyze`, `trigger_type='manual'` + `requested_by` 감사 기록). **사람이 중요하다고 본 저점수 사례**로 RAG에 태깅되어, 점수 체계가 놓치는 패턴의 학습 자산이 된다 (2026-07-14 PM 확정 — 게이트 3중화 ③).

### 예시 5 — PM 직후 (점수 이전 단계에서 차단)
요란 PM 후 C17 레벨 +317 이동. 구 기준선이면 이후 전 wafer가 위반 = 하루 231건 폭주. → **가한계 Phase 0(알람 억제) → Phase 1(광폭 4~5σ + provisional 플래그)**로 알람 생성 자체를 막고, Phase 2 정착 후 정식 재산정. 점수가 아니라 **기준선 수명주기**로 푸는 원천 ④.

### 예시 6 — 치우침 그룹 (오탐 생성 자체 감소)
KEEP\* 6그룹(C6_0): ±3σ면 오탐 4.43% = 4챔버 ~245건/일. → **분위수 관리선(q 0.00135/0.99865) + σ-존 룰(N1·N5~N8) 제외, σ-무관(N2·N3·N4)만 적용** → 오탐 0.30% = **~17건/일 (−93%)**. 가드: Scorecard(M2·M8) **미탐 0건** — 미탐 발생 시 즉시 ±3σ 전체 룰 회귀 (헌법 1-1 예외 2).

## 6. 왜 31인가 + 미확정·검증 계획

- **31 경계**: 가안 배점 기준 "축 1개 + α"(최대 ~25)와 "축 2개 수렴"(최소 ~30대)의 분리선. 확정 근거는 시뮬 Scorecard로 실측 튜닝한다 — 목표는 **미탐 0 유지 하에 Agent 호출 최소화** (오탐 필터가 미탐을 만들면 실패. 미탐 가드는 M2·M8).
- **미확정 3건**: ⓐ 산식·배점 (B4-1, B) ⓑ `context_score_pred_weight` (B4-1 착수 시 B 기입) ⓒ **Nelson 룰 프루닝** *(2026-07-19 멘토 피드백 — "알람 개수 자체를 줄이고 룰 수도 줄여라")*: 실데이터 리플레이로 룰별 오탐/미탐 기여도를 채점(Scorecard 확장)한 뒤 기여 없는 룰 비활성 — **실데이터 확인 전 결정 금지** (멘토 단서 그대로), 소유 B, 가드는 동일(미탐 0).
- **주의**: predicted_c65 축은 **단독으로 알람·점수를 발동할 수 없다** (예측 모델 오차가 알람 소음의 새 원천이 되는 것을 차단 — 7/10 확정). 가한계 Phase 0~1에서는 가중 자동 0 (재학습 전 예측 신뢰 불가 구간).

## 7. 예상 질문 & 답변 (발표·멘토링 대비)

**Q1. 31이라는 숫자의 근거는?**
가안 배점에서 "축 1개짜리 소음"은 최대 ~25점, "축 2개 수렴"은 30점대부터 시작 — 그 분리선이다. 단, 숫자 자체를 방어하지 않는다: config 등재값이고, Scorecard로 **미탐 0 유지 하에 호출 최소화** 기준으로 실측 튜닝한다. "31이 옳다"가 아니라 "31을 검증·조정하는 체계가 있다"가 답.

**Q2. 점수 필터가 진짜 사건을 놓치면 (미탐 책임)?**
3중 방어다: ① critical은 점수를 안 보고 즉시 가동 ② Scorecard 미탐 가드 — 미탐 1건이면 필터 롤백 ③ 엔지니어 수동 요청 탈출구. 그리고 저점수 알람도 기록·병합은 전부 되므로 사후 추적이 끊기지 않는다. 우리는 알람을 죽이는 게 아니라 호출만 미룬다.

**Q3. 오탐율 1.1%·4.43%는 어디서 나온 수치인가?**
1.1%는 관리도 문헌(Montgomery) — 감도 룰 전체 적용 시 ARL₀ 370→92의 역수. 4.43%는 우리 실데이터 실측(B, KEEP\* 6그룹 ±3σ). 이론치와 실측치를 분리해서 제시한다.

**Q4. "수백 건"은 시뮬 얘기 아닌가? 실팹 근거는?**
산수의 재료가 전부 실데이터다 — 처리율 231장/일(실측), 오탐율 4.43%(실측), 그룹 구조(실데이터 스텝·센서). **장비 1대(4챔버) 기준** 보수 추정이고 실팹은 베이당 장비 여러 대 × 베이 수십 개이므로, 현업 알람 피로(상용 FDC 공통 불만)와 방향이 정합한다. 오히려 우리 숫자가 과소 추정이다.

**Q5. 예측치(predicted_c65)를 점수에 넣으면 모델 오차가 알람을 오염시키지 않나?**
그 위험 때문에 3중 제한을 걸었다: 단독 발동 불가(가중항만) + 가한계 Phase 0~1 가중 자동 0(재학습 전 예측 불신 구간) + 가중치 자체를 미확정(null)으로 두고 B4-1에서 실측 후 확정. 예측 채널은 "보태는 증거"지 "울리는 트리거"가 아니다.

**Q6. 오탐이 늘 걸 알면서 왜 룰 8개를 다 켜나?**
안 켠다 — 2단으로 줄인다 *(2026-07-19 멘토 피드백 반영)*. **상류: 룰 프루닝** — 실데이터 리플레이에서 룰별 오탐/미탐 기여를 채점해 기여 없는 룰은 끈다 (KEEP\* 그룹은 이미 N1·N5~N8 제외로 선례가 있다 — 룰 축소는 이미 하고 있는 일의 일반화). **하류: 점수 게이트** — 살아남은 룰의 잔여 오탐을 수렴 점수로 거른다. 룰을 무엇을 끌지는 이론이 아니라 실데이터 채점(Scorecard)으로 결정하며, 기준은 동일하게 미탐 0 유지다.

**Q7. AE는 이상이라는데 Nelson은 정상이면 — 채널이 충돌하는 것 아닌가?**
충돌이 아니라 보완이다. 각 센서가 한계 안이어도 조합이 낯선 경우(예: C31 정상인데 C11만 얕아짐 — 상관 −0.978 붕괴)는 Nelson의 구조적 사각이고, 그때 AE 축이 점수를 올려 게이트를 넘기는 게 정상 동작이다. AE는 알람 권한이 없으므로(헌법 1-2) 단독으로 소음을 만들 수도 없다.

**Q8. Incident당 pending 1건이면 병목 아닌가?**
"동시 1건"은 **같은 Incident 안**의 규칙이다 (헌법 1-4 P3 해석 명문). 다른 Incident끼리는 병렬이고, 같은 Incident도 순차 승인은 여러 번 가능하다. 취지는 속도 제한이 아니라 같은 사건에 모순된 결정 2개가 동시에 열리는 것의 차단.

**Q9. 수동 요청이 남발되면 결국 알람 피로 재발 아닌가?**
`requested_by` 감사 기록 + Incident당 동시 분석 1건이 남발을 구조적으로 제한한다. 그리고 수동 요청 빈도 자체가 지표다 — 잦다면 게이트가 못 미덥다는 신호이며, 그 사례들이 RAG에 태깅되어 배점 개선 재료가 된다. 남발조차 학습 데이터로 회수하는 설계.

**Q10. 분위수 관리선은 SPC 표준(±3σ) 위반 아닌가?**
분포가 비정규인 그룹에 ±3σ를 강요하는 쪽이 통계적으로 틀렸다 — 실측 오탐 4.43%가 그 증거고, 분위수(±3σ 등가 q=0.00135)로 0.30%까지 내려간다. 헌법 1-1 예외 2로 명문화했고, 멘토 확인 완료(7/11), 미탐 0 가드 + 위반 시 즉시 ±3σ 회귀 조건부다. 6그룹 한정이며 σ-무관 룰(N2·N3·N4)은 유지된다.

**Q11. PM 직후 알람 억제(Phase 0)는 위험하지 않나 — 제일 예민한 시기인데?**
무감시가 아니다. Phase 0는 Qual 검증까지의 짧은 구간이고 그동안 Qual 4지표가 별도로 감시한다. Phase 1부터는 억제가 아니라 광폭 한계(4~5σ)+provisional 플래그로 "느슨하지만 켜져 있는" 상태다. 구간별로 감시 주체가 바뀔 뿐 공백은 없다.

**Q12. 배점을 B 한 사람이 정하는 게 맞나?**
산식 소유는 판정 엔진 오너(B)가 맞지만 — 값은 config 등재(PR 리뷰 대상), 검증은 Scorecard(팀 공동 자산), 경계 변경은 계약 문서 동기화 의무가 걸린다. 확정 전까지 null로 명시하는 규율 자체가 "혼자 조용히 정할 수 없는" 구조다.
