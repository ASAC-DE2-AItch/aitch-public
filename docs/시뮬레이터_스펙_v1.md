# 시뮬레이터 스펙 v1.2 — 가상 Fab (Scenario Replay Engine)

> 소유권: `src/simulator` (PM/PO — 헌법 3-1). 기획서 v4.4 3-4-1절의 구현 명세.
> **사이클 세계관의 단일 소스는 `docs/사이클_정의_v1.md`** — 개방 간격·대PM 승격·레짐 리샘플·Qual 발행·다운타임·hour 프로파일 등 생성 규칙은 사이클 정의 §3을 따른다. 본 문서는 엔진 구조·YAML 스키마·채점 명세만 관리.
> **핵심 원칙 (조작 경계)**: 시뮬레이터는 **fdc.raw 위쪽(데이터 생성)만** 제어한다. 파이프라인 내부 상태(판정·Incident·승인)는 어떤 경로로도 조작 불가 — 이 경계가 "시연은 자작극이 아니다"의 방어선이다. 시뮬레이터가 하는 일은 이상한 데이터를 흘려보내는 것까지고, 잡아내는 것은 온전히 시스템의 몫이다.
>
> **v1.2 갱신 (2026-07-08)**: ① 처리율 **231 wafer/일** (구 170 정정 — 사이클 정의 F1). ② **hour 프로파일** — Y에 시간대 오프셋 부여(`config/hour_profile_v1.csv`, 진폭 41). ⚠ **적용은 합성 Y 생성 단계에서만** — 현재 Replay Engine은 실데이터 C65를 그대로 재생하므로 hour 효과가 이미 포함, 지금 더하면 이중 계상. ③ pm_reset 시나리오의 레짐 라벨은 유형이 아니라 **판정(조용/요란)** 기준(사이클 정의 §2).
> **v1.3 갱신 (2026-07-20, 멘토 피드백)**: **가상 챔버 6 → 4 확정** — 세계관 = **Etch 클러스터 장비 1대(PM 4개)**. 멘토 현장 경험(하이닉스 Etch 장비 4챔버 구성) 기준. 상용 플랫폼 최대치는 6+(TEL Tactras 6, AMAT Sym3 6+클린2)이나 챔버 수는 주문 구성이므로 실무 표준 구성을 따른다. 챔버 수는 config(`n_chambers: 4`)로 유지. 용어 정정: 우리 시뮬 범위는 "베이"가 아니라 **장비(Tool) 1대** — 베이 = 장비 여러 대의 구역.

## 1. 3층 구조

```
┌─ ① Replay Engine ──────────────────────────────────────┐
│  train_data.csv → wafer 단위 시간순 재생 → fdc.raw 발행 │
│  · 배속 조절 (실제 3초 간격 → 데모 0.1~1초)             │
│  · 멀티챔버 복제: 실데이터(1챔버)에 챔버별               │
│    오프셋+노이즈 프로파일을 입혀 가상 4챔버 생성          │
│    (= Etch 클러스터 장비 1대의 PM 4개 — v1.3)            │
│    (오프셋은 실데이터 분산 범위 내 — 챔버 "개성")        │
└──────────────────────┬─────────────────────────────────┘
                       ▼
┌─ ② Scenario Injector ──────────────────────────────────┐
│  YAML 시나리오 config에 따라 정상 스트림 위에            │
│  이상 패턴을 덧씌움 (additive/override)                 │
│  · 패턴 타입: ramp / spike / shift / oscillation        │
│               / pm_reset / qual_mode                    │
│  · 진성 이상 시나리오는 C65 라벨도 상응 상승 생성        │
└──────────────────────┬─────────────────────────────────┘
                       ▼
┌─ ③ Ground Truth Log (sim_events) ──────────────────────┐
│  주입한 모든 이벤트를 정답 라벨과 함께 기록              │
│  → 시스템 판정과 대조하여 자동 채점 (Scorecard)         │
└─────────────────────────────────────────────────────────┘
```

## 1-1. P5-3 본대 (2026-07-20 구현) — pm_reset 패턴 + BL8 목표 지정형

**pm_reset (요란 레짐 전환 재현)** — 실측 리셋 사건(train wafer idx 3692, 전후 100·300장 창)의 재현:

| 축 | 실측 | 주입 (공학단위 — σ 분모 모호성 차단) |
|---|---|---|
| C17 정착 레벨 | −37.7 (N=300, −0.81σ / N=100 −0.7 — 창 민감, 방향 일관) | `level_shifts_eng: {C17: -37.7}` 영구 계단 |
| C11 wf_min | +8.85 (+5.0~5.4σ, 창 무관 안정 — F14) | `ignition_shifts_eng: {C11: 8.85}` **과도행(C42=1) 한정** → 정착 평균 침묵 유지 |
| C9 | 레짐 계단 없음 (동행은 wafer 내 궤적 얘기) | **주입 안 함** — C17·C9 관계 붕괴 자체가 AE 반응의 실측 근거 |
| Y (C65) | +921~958 (pre ~620 → post ~1,560) | `y_shift: 940` — **fdc.actual 경유만** (raw 미포함, 헌법 1-3) |

동작: 트리거 시 ⓐ C33 리베이스(원본−기준+1 — 증가 리듬 보존, B의 PM 감지 정합) ⓑ producer가 `pm_bumps()`로 pm_count 가산 → QualPublisher 5장 자동 발행 ⓒ sim_events에 shifts·y_shift 포함 기록. 확장 후보(주입 안 함 — 레짐 반응 실측 미검증): C32 과도·C54/C56·C15/C16. ※ 구 인용 "+317"은 BL3 프라이어 추정치 계열로 추정 — A 산정 창 대조 항목 (v5.2).

**BL8 temp 목표 지정형 (recipe_applier)** — temp는 setpoint 컬럼이 수집 밖이라 delta 불성립 → `parameter_id: temp_target` + `value_current/proposed`(목표 운전점)로 지정, 시뮬이 C17 모니터 채널을 **서보 근사 수렴**(TAU 30 wafer 선형 램프 — 즉시 계단 금지)으로 반영. D6 ±3% 준용(초과 거부), sim_events `adjust_mode: target` 기록. C17 손잡이 금지 원칙과 비충돌 — 조작 대상은 temp_target 물리 목표, C17은 결과 모니터. dry-run R1~R6+T1~T3 = 9/9 PASS.

## 2. 시나리오 YAML 스키마

```yaml
scenario_id: drift_after_pm          # 고유 ID
name: "PM 후 기준선 노후 Drift"
description: "PM 직후 정상 상태 이동 — 정답: 실력치 재설정"
target_chamber: SIM_CH_3
duration_wafers: 200                 # 시나리오 길이
injections:
  - at_wafer: 0
    event: pm_reset                  # C33 리셋 + 분포 shift
    shift_source: train_pm_segment   # 실데이터 PM 구간(C33 리셋 전후)에서 추정한 파라미터
  - at_wafer: 20
    sensor: C11                      # Vdc
    pattern: ramp
    magnitude_pct: +4.0
    duration_wafers: 30
c65_effect: none                     # 가성 — 실제 품질 영향 없음
ground_truth:
  type: benign_shift                 # 정답: 기준선 노후
  correct_action: limit_correction   # 정답 조치: 실력치 재설정
  correct_disposition: RELEASE
```

**패턴 타입 정의**

| 패턴 | 동작 | 유도하는 신호 |
|------|------|--------------|
| `ramp` | 점진 증감 | N2/N3 (추세) |
| `spike` | 단발 급변 | N1 (Critical) |
| `shift` | 계단형 평균 이동 | N5, Drift Score |
| `oscillation` | 증감 반복 | N4 |
| `pm_reset` | C33 리셋 + 분포 이동 | PM 이벤트 |
| `qual_mode` | QUAL 상태 진입 + is_qual wafer N장 발행 | RECOVERY_VERIFY |

## 3. QUAL 모드 상태머신

```
RUN ──(pm_reset 주입)──→ PM_OFFLINE ──(트리거)──→ QUAL
  QUAL: is_qual=true wafer N장(기본 5) 발행 → 파이프라인이 평가
   ├─ 엔지니어 승인(S7) → ChamberRequalified → RUN
   └─ 미통과 → 추가 Qual 발행 또는 PM_OFFLINE 복귀
```

- `fdc.raw`에 `is_qual` 필드 추가 필요 — **스키마 변경, 소비자(A·B) 리뷰 필수 (헌법 2-2)**
- Qual 성공 시나리오: PM shift가 정상 안착한 분포로 Qual trace 생성
- Qual 실패 시나리오: 오염/오조립 잔류를 가정한 비정상 거동 유지

## 4. C65 라벨 생성 규칙

- 가성 시나리오(`c65_effect: none`): 실데이터 C65 분포 그대로
- 진성 시나리오(`c65_effect: degrade`): 주입 심각도에 비례해 C65 상승 (계측 모사) — Disposition 판정(SCRAP 정답)의 근거

## 7. Scorecard — 자동 채점

시나리오 종료 후 sim_events(정답)와 시스템 기록(incidents, approval_records, wafer_dispositions)을 대조:

| 채점 항목 | 대조 | 매핑 지표 |
|----------|------|----------|
| 감지 여부·지연 | 주입 시점 vs 첫 alert | M2, M8 |
| Incident 그룹핑 | 알람 수 vs Incident 수 | M13 |
| 라우팅 정확성 | 정답 조치 vs Supervisor 추천 | M12 |
| 실력치 재설정 적절성 | 섀도 평가 가성알람/미탐 | M5 |
| Disposition 정확성 | 정답 vs 시스템 권고 | — |
| Qual 판정 | 정답(pass/fail) vs 판정 | 오탐/미탐율 |

**시연 마무리 연출**: 시나리오 공개 실행("지금 이상을 주입합니다") → 시스템이 잡는 과정 시연 → Scorecard 공개("주입한 정답과 시스템 판정 대조") — 주입 사실을 숨기지 않아도 설득력이 성립하는 구조.
