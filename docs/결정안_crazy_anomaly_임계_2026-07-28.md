# 결정안 — crazy wafer 판정의 anomaly 임계 (`spc.crazy_wafer.anomaly_score_min`)

> 작성 PM (2026-07-28). 대상: A(팀원 A)·B(팀원 B)·C(팀원 C) 확인 → 확정 시 `config/params.yaml` 등재.
> 배경: C 구현(#57)이 이 키를 **선택적**으로 읽고, **미설정이면 SCRAP을 내지 않는다**(fail-safe).
> 즉 지금 상태로 M3에 가면 "한 장만 튀면 스크랩" 장면에서 **SCRAP 권고가 나오지 않는다.**

## 1. 결론 (제안)

```yaml
spc:
  crazy_wafer:
    predicted_c65_threshold: 1572     # (기존) train P99
    anomaly_score_min: 0.5            # 🆕 = AE 보정 앵커 P99.5 (상위 0.5%)
    anomaly_score_multiplier: 3.0     # (사문화 — 아래 §4. 유도 근거로만 보존)
```

**값 = 0.5 · 근거 = "3배"가 아니라 "퍼센타일".** 사유는 §3.

## 2. 그동안 못 정한 이유와, 지금 풀린 이유

B9 원문은 `anomaly_score > 3×기준`인데 **"기준"이 무엇인지 정의된 적이 없었다.** 그래서 C가
값을 못 넣고 fail-safe로 막아둔 것이 맞다.

이번에 AE 번들(`models/anomaly_ae/ae_v1/calib.json`)을 열어 확인한 결과 **스케일이 이미 확정돼
있었다.** 보정 방식이 `ecdf_anchor`, 즉 **ae_score는 값 자체가 퍼센타일에 고정**된다:

| ae_score | 퍼센타일 | 빈도 |
|---|---|---|
| 0.05 | P50 | — |
| 0.10 | P90 | — |
| **0.20** | **P98.5** | 상위 1.5% ← `qual_threshold`로 calib에 박혀 있음 |
| **0.50** | **P99.5** | 상위 0.5% (1만장당 50장) |
| 1.00 | P99.9 | 상위 0.1% |

계약서도 같은 값을 명시한다 — *"anomaly_score = ae_score [0,1], **0.2 = Qual/알람 참조 임계**"*
(`qual.pass_ae_max`·`ct.ae_anomaly_threshold`와 동일). **즉 B9의 "기준" = 0.2로 확정 가능**하고,
3×0.2 = **0.6**이 문구 직역값이다.

## 3. 그런데 0.6이 아니라 0.5를 제안하는 이유

**⚠️ 퍼센타일 축에서 "3배"는 의미가 없다.** ae_score는 선형 크기가 아니라 순위 눈금이라,
0.2→0.6이 "3배 더 이상하다"를 뜻하지 않는다. 실제로 계산하면 두 후보는 **거의 같은 지점**이다:

| 후보 | 퍼센타일 | 빈도 | 성격 |
|---|---|---|---|
| 0.6 (=3×0.2 직역) | P99.58 | 상위 0.42% | 보간값 |
| **0.5 (제안)** | **P99.50** | 상위 0.50% | **보정 파일에 실재하는 앵커** |

차이가 0.08 퍼센타일(1만장당 8장)이라 **어느 쪽이든 실무 영향은 사실상 없다.** 그렇다면
ⓐ 보간이 필요 없고 ⓑ "상위 0.5%"로 한 줄 설명이 되며 ⓒ 아래 §5의 AND 구조에서 조금 더 여유가
있는 **0.5**를 택하는 게 낫다. **회의에서 0.5 대 0.6을 논쟁할 필요는 없다** — 같은 지점이다.

기록용 문장: *"anomaly 임계 = 0.5. 근거는 3배 곱셈이 아니라 AE 보정 앵커 P99.5(상위 0.5%)이며,
B9 원문 '3×기준'의 직역값 0.6과 0.08 퍼센타일 차이라 실질 동등하다."*

## 4. 덤으로 발견한 정리 사항

`anomaly_score_multiplier: 3.0`은 **`src/common/context_score/publisher.py`가 읽는다**
(브랜치 `feat/common-contextscore` — push됨·dev 미머지, dev+34). `CrazyConfig.anomaly_cut`
프로퍼티가 `multiplier × C6(ct.ae_anomaly_threshold=0.2) = 0.6`으로 **알람 arm 컷을 동적 산출**
하며, 키 부재 시 `_key`가 명시 실패(KeyError)한다 — 매직넘버 대체 금지(6-1) 설계.

> ⚠️ **PM 조사 오류 정정 (2026-07-29)**: 앞서 "읽는 코드 0건"이라 한 것은 ⓐ 워킹트리(dev 체크아웃)
> 검색 ⓑ 브랜치 순회 시 목록에 `head -20`을 걸어 알파벳순 뒤쪽인 `feat/common-contextscore`가
> **잘려나간** 결과다. 정보 부재가 아니라 검색 범위 실수. → 교훈: 브랜치 전수 검색은 절단 금지,
> 단정 표현에는 범위를 명시할 것.

**⚠️ 따라서 전환 순서가 강제된다 (B 지적 채택)**:
```
① publisher.py 가 절대 키(anomaly_score_min)를 읽도록 변경   ← 먼저
② 그 뒤 anomaly_score_multiplier 주석 처리                    ← 나중
```
역순이면 ⓐ 주석만 먼저 → KeyError로 **crazy 판정 자체가 미발동** ⓑ 키를 살려둔 채 절대값만 등재
→ 컷이 0.6으로 남아 **0.5가 무시**된다. 코드·테스트는 **B가 처리**(2026-07-29 합의).

부수 확인: `multiplier × C6 = 3.0 × 0.2 = 0.6`은 §2의 PM 유도값과 정확히 일치 — B 구현이 이미
"기준 = 0.2" 해석으로 돌고 있었다는 상호 검증이 됐다.

**세 곳이 한 키를 공유한다 — 방향이 반대임에 주의**: 전환 후 이 키를 읽는 곳은 셋이고,
각자 원하는 방향이 상충한다.

| 사용처 | 원하는 임계 | 이유 |
|---|---|---|
| 알람/HOLD 컷 (publisher) | **낮게** | 미탐 비용 큼 · HOLD는 가역(공짜) |
| §8 RELEASE 가드 (STEP 2) | **낮게** | 무효 예측을 걸러야 함 |
| SCRAP 확인 (STEP 4) | **높게** | 오폐기는 되돌릴 수 없음 |

현재 0.5는 셋 다 만족하나, **한 손잡이가 상반된 안전 목표를 겸한다.** 올리면 오폐기↓·미탐↑,
내리면 반대. 지금 키를 쪼갤 필요는 없고(값 하나로 성립), **튜닝 시 세 곳 영향을 함께 볼 것**만
기록한다. 필요해지면 `alarm_anomaly_min` / `scrap_anomaly_min` 분리(scrap ≥ alarm)가 정석.

케이스 정합 확인 (구멍 없음): ①예측 초과+이상 → 알람·SCRAP ②예측 초과+정상 → 알람·HOLD
③예측 정상+이상 → 알람 + §8 가드로 HOLD(계측 대기) ④둘 다 정상 → 무반응.

**⚠️ 절대값 전환의 대가 — C6 자동 추종 상실**: 현 publisher는 `anomaly_cut`을 프로퍼티로 두어
*"C6 재튜닝 시 자동 추종"*(코드 주석)하도록 설계돼 있다. 절대 키로 바꾸면 이 연동이 끊긴다.
그래도 절대값을 택하는 이유는 우리 근거가 "C6의 배수"가 아니라 **보정 앵커 P99.5**이기 때문이다.
대신 끊긴 연동은 절차로 메운다 — **AE 재캘리브레이션 체크리스트에 "C6와 anomaly_score_min을
새 앵커로 함께 재유도" 항목을 넣는다** (AE 포화 §7ⓑ 대응이 곧 재캘리라 즉시 해당).

## 5. ⚠️ 함께 확인해야 할 것 — OR인가 AND인가 (더 중요)

B9은 `c65 > 1572` **또는** `anomaly > 3×기준`(OR)인데, C의 판정 트리는 다르다:

```
STEP 2. c65 ≤ 1572                    → RELEASE      ← c65가 관문
STEP 3. 초과 2장 이상                  → HOLD  (여러 장 = 공정 문제, R2R 경로)
STEP 4. 초과 1장 + anomaly ≥ 임계      → SCRAP ← 사실상 AND (이중 확인)
        그 외                          → HOLD
```

**이건 모순이 아니라 층이 다른 것으로 정리하면 맞다:**
- **B9의 OR** = *알람/자동 격리(HOLD)* 조건 — 어느 한 축만 튀어도 일단 잡아둔다 (보호, 비용 없음)
- **C의 AND** = *SCRAP(폐기)* 조건 — 되돌릴 수 없으니 자 두 개가 같이 가리켜야 한다

이 해석을 셋이 합의하고 계약서에 한 줄 남기면 종결된다.

**단, M3 시연에 직결되는 결과가 있다**: SCRAP 장면이 나오려면 주입한 wafer가
**`predicted_c65 > 1572` 와 `anomaly_score ≥ 0.5` 를 동시에** 만족해야 한다. 한쪽만 튀면 HOLD까지만
간다. 리허설에서 이 두 값을 눈으로 확인하고, 안 나오면 주입 크기를 키워야 한다 (시나리오 파일의
spike 크기 상향).

## 7. 실측 후속 (2026-07-29 — 프로브·완전 리허설 결과)

**ⓐ 모델 감도 프로브 결과: 전 조합 미돌파 (`probe_scrap_report.txt`).**
C31·C11·C17·C62·C4 × 4~10σ 부스트 20조합 전부 predicted_c65 1572 미달 — 최대 반응이
C11 +8σ → **Δ+5.0** (1019). 트리 모델(XGBoost)은 학습 분포 밖 값에서 리프가 포화되어
외삽하지 않는다 — 학습 데이터에 "센서 급변 → C65 폭등" 사례가 희소하니 그 관계 자체가
학습되지 않았다. C4는 Δ 0.0(사실상 미사용 피처), C17·C62는 음의 반응(방향성 학습).

**결론: M3 SCRAP 시연 = B안 확정** (HOLD까지 + "자 하나로는 폐기하지 않는다" 설명).
센서 유발 spot은 예측 축(c65 arm)으로 잡히지 않는 것이 현 모델의 실측 실력이며, 이는
발표 재료로도 유효하다 — *"모델은 분포 밖을 외삽하지 않는다. 그래서 이중 확인과 사람
승인이 있다."* → **A(팀원 A) 과제 전달: spot 감도** (급변 파생 피처 또는 별도 rule-assist).

**ⓑ 신규 발견 — AE 라이브 포화 (완전 리허설 [8]).**
`LEAN85_AE_MODE=live` 상태에서 예측 200건 **전부 anomaly ≥ 0.5, max=1.0**. 더미 폴백은
uniform(0.01~0.15)이라 이 분포가 나올 수 없다 — **AE 실추론이 켜졌고, 시뮬 세계 전체를
극단 이상(P99.5+)으로 판정 중**이다. 주입 없는 챔버까지 전량 포화이므로 주입 탓이 아니라
**시뮬 리플레이 조건**(가상 챔버 SIM_CH_1~4 conditioning 미학습 또는 ±0.5σ 챔버 오프셋)이
유력하다. 영향: SCRAP AND는 c65 축이 막아 오폐기는 없음(fail-safe 성립)이나, **Qual AE
지표(0.2 기준)가 전량 FAIL → '조용' Qual 판정이 불가능**해진다 — M3(요란 시연)는 무영향,
조용 케이스·시나리오 확장에 블로커. → **A(팀원 A) 확인 요청**: AE 번들의 챔버 조건화가
SIM_CH_* / 오프셋 세계에서 유효한지 (재캘리브레이션 또는 시뮬 챔버 매핑).

**ⓒ anomaly_score_min=0.5 제안은 유지**하되, ⓑ 해소 전까지 실질 의미는 "AE 정상화 후"
기준임을 명시한다. 포화 상태에서는 어차피 c65 축이 SCRAP을 막는다.


## 8. ★PM 결정 — RELEASE는 "유효한 예측"에만 (STEP 2 anomaly 가드 필수화, 2026-07-29)

§7ⓐ의 귀결: 분포 밖 급변 wafer는 예측이 정상으로 남아 **STEP 2에서 RELEASE 권고**가 나온다.

**원칙 (PM 확정)**: anomaly 점수는 품질의 제2의 자가 아니라 **예측 유효성 게이트**다 — AE가
탐지하는 것이 정확히 "이 입력이 모델이 학습한 세계 안인가"이므로. 따라서 권고의 의미론은:
- 예측모델이 **자격 있는 입력을 정상 판정** (AE 정상 + 예측 정상) → RELEASE
- 예측모델이 **판정할 자격이 없는 입력** (AE 이상 — 예측값 자체가 무의미) → **HOLD (계측 대기)**
"모델 한계로 정상처럼 보이는 것"과 "정말 정상인 것"을 권고가 구분해야 한다는 것 (7/29 PM 결정).

**개정안 (C 판정 트리 — 팀원 C님 구현 요청, 필수)**:
```
STEP 2. 예측 ≤ 1572
        └ anomaly < 임계  → RELEASE          (현행 — 품질·이상 둘 다 무근거)
        └ anomaly ≥ 임계  → HOLD (계측 대기)  🆕 자 하나가 "이상"을 가리키면 실측 전 미해제
```
SCRAP(STEP 4)의 이중 확인 대칭 원리와 같다 — SCRAP은 자 2개가 "불량"을 가리켜야 하고,
RELEASE는 자 2개가 "정상"을 가리켜야 한다. 한쪽만 정상이면 중간값(HOLD·계측)이 정답.

시연 함의: 급변 wafer가 RELEASE 권고로 떠도, 엔지니어가 **modify로 SCRAP/HOLD 수정 승인**
하는 장면 자체가 최강 HITL 시연 (수정 영속은 B-2에서 확보 완료). 트리 개정과 무관하게
이 장면은 지금도 가능하다.

**적용 순서 (중요 — 키 등재가 스위치)**: 가드와 SCRAP이 같은 키(`anomaly_score_min`)를 쓰므로,
AE 포화(§7ⓑ) 상태에서 등재하면 ⓐ RELEASE 전멸(전량 "이상") ⓑ 포화 anomaly가 SCRAP의 절반-
가짜 근거가 된다. 따라서 **값(0.5)은 3자 합의로 확정하되, params 등재는 AE 정상화 후에** 한다 —
포화 상태에선 SCRAP도 어차피 유효하게 못 나오므로 잃는 것 없음. 등재 시점 = "SCRAP 개통 +
RELEASE 가드"가 유효한 상태에서 동시에 켜지는 단일 스위치. (§1·§6의 "확정 시 등재"는 이 순서로 정정)
