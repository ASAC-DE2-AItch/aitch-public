# TSR-0004: 시뮬 producer 중복 기동 — 예외 없이 적재만 멎는다 (timestamp 역전 전량 드랍, 40분·42분 2회)

## Status

Resolved

## Context

- **발생일**: 2026-08-06 13:36~14:16 (1차 40분) · 2026-08-07 01:00~01:42 (2차 42분 — 잔해 재생).
  항구 조치 2026-08-07 02:40. 본 문서는 8장 30분+ 기록 의무의 소급 이행(2026-08-09 작성).
- **담당자**: PM (시뮬레이터 소유 — 헌법 3-1)
- **관련 컴포넌트**: `src/simulator/kafka_producer.py` · `simulator_runner.py`(S11 RUN) ·
  `src/agent_b_spc/spc_consumer.py` 단조성 가드 · `consumer-group-spc` 오프셋
- **증상**: 화면 알람 정상 · 예외/ERROR 0 · **`spc_violations` 적재만 0.**
  `incident_alerts` 는 별 프로세스(grouper)라 계속 증가해 혼선을 키웠다.
- **왜 늦게 발견됐나**: 드랍이 예외가 아니라 **가드가 설계대로 버린 것**이라 ERROR 가 없다.
  게다가 진단 중 docker 로그를 한글 패턴으로 grep 해 3회 연속 "그런 로그 없음"으로 오진했다
  (`역전` → `??쟾` 인코딩 파손 — 7장 기등재 항목의 실측 원본이 이 사건이다).

## Decision

### 근본 원인 — 역전 ⟺ producer 2개 (필요충분)

`message_builder.py:130` 의 `timestamp` 는 원본 C10 이 아니라 **발행 시각 wall-clock**
(`datetime.now(timezone.utc)`)이다. 따라서:

- 루프 재생·오프셋 backlog 재생으로는 타임스탬프가 항상 증가 — **역전이 원리적으로 불가능**하다.
- 단일 producer 는 `key=chamber_id` 발행이라 파티션 내 순서가 보장된다(kafka_producer.py:192).
- 역전은 **두 producer 가 같은 파티션에 동시 발행하며 각자의 배치·linger 타이밍이 엇갈릴 때만** 생긴다.

역전이 생기면 consumer 단조성 가드가 `timestamp 역전 → 드랍` 으로 전량 폐기한다. 판정 로그는
계속 찍히므로 겉에서는 정상이다.

### 유발 경로 — 가드가 "띄우는 쪽" 프로세스 메모리에만 있었다

S11 RUN 은 이미 도는 producer 가 있어도 자기 producer 를 새로 띄운다(UI 가 자기 자식만 추적).
구 `RunnerBusy` 가드는 상주화(7/28, M3 ②) 때 무력화됐고, 남은 판정이 게이트웨이 프로세스
메모리(`self._proc`)뿐이라 두 경로가 열려 있었다: ⓐ CLI 직접 기동 ⓑ 게이트웨이 재시작 후 고아.

### 2차(8/7 01:00)는 새 사고가 아니라 1차의 잔해 재생

`consumer-group-spc` 의 `fdc.raw` LAG 이 **400,584건** — 오후 사고 구간이 토픽에 남아 있고
`enable.auto.commit=False` 라 재시작마다 그 구간부터 재소비한다. 두 스트림이 교차 재생되며
같은 챔버에 wafer 두 계열이 섞여 → 역전 드랍 → 적재 정지 재현. 조치는 오프셋
`--reset-offsets --to-latest`(부작용: `--all-topics` 라 `fdc.agent` 8건 동반 스킵 — 경미로 판정).

### 채택 해결 — 가드를 띄우는 쪽이 아니라 **떠지는 쪽**에, 프로세스 메모리가 아니라 **OS 레벨**로

`src/simulator/single_instance.py` 신설: producer 자신이 `127.0.0.1:47651` 포트를 bind(OS 뮤텍스).
프로세스가 어떻게 죽든 OS 가 해제하므로 **stale lock 이 없다.** Windows 함정 2종을 코드·테스트에
고정: **`SO_REUSEADDR` 금지**(Linux 와 의미 반대 — 켜면 중복 bind 가 허용돼 가드가 조용히 무력화)
· `127.0.0.1` 고정(`0.0.0.0` 은 방화벽 팝업).

### 검토했으나 채택하지 않은 안

| 안 | 기각 사유 |
|---|---|
| S11 러너에서 프로세스 목록 검사 | "띄우는 쪽" 가드 — CLI 직접 기동을 못 막고, 러너 재시작 시 고아를 추적 못 한다 |
| PID 파일 락 | 강제 종료 후 stale lock → 재기동 불가가 원 문제보다 나쁘다 |
| consumer 역전 가드 완화(역전 수용) | 판정 시계열 오염 — 가드는 옳다. 원인(중복 발행)을 막는 것이 정공 |

## Consequences

**검증 (2026-08-07 02:40)**: 신규 테스트 7 + 회귀 8 = 15 passed · 두 번째 producer **rc=2 거부**
(선점 PID 힌트 표시) · 역전 로그 0줄 · `spc_violations` 적재 지연 0.4초.

**락 실전 실증 누적 3회**: 8/7 02:40 최초 + **8/9 리허설 왕복 2회**(단일 패스 기동마다
"🔒 단일 기동 락 획득" 확인 — TSR-0005 의 왕복이 부수 실증).

**남은 리스크**

- **오프셋 재생 구조는 잔존** — 사고 구간이 토픽에 남아 재시작마다 재현될 수 있다.
  소비 측 역전 내성(챔버별 last_dt 재초기화)은 발표 후 검토(상황판 A8).
- **적재 정지 자체를 감지하는 장치 부재** — 원인이 무엇이든 "마지막 성공 적재 후 N분 경과 시
  WARN" 이 필요하다(1차·2차가 증상은 같고 원인이 달랐다). 발표 후 WP 후보.
- 가드 이전 버전 프로세스가 떠 있을 수 있으므로 기동 전 `kafka_producer` 1개 확인 절차는
  유지한다(런북·7장 기등재).

**재발 방지** — 7장에 이 사건 계열 3항이 이미 등재돼 있다(producer 2개 금지 · 한글 grep 함정 ·
OS 레벨 단일 기동 가드). 본 PR 은 기록 의무 이행 + 인접 함정(PS 5.1 내장 인용부) 추가분.
