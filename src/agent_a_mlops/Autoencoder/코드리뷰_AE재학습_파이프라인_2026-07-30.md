## 총평

**전반 품질은 매우 높다.** 게이트 항진명제 제거(홀드아웃 분리), 프로브의 결정적 채점(난수 0), 판정(exit 2)/실행 오류(exit 1) 구분, 분모 이중 캡, RUNNING 원자 선점, "감사 먼저·신호 나중" 순서, 자기 롤백 방어 등 설계 결정마다 근거가 문서화되어 있고 헌법 조항 참조도 정확하다. 헌법 1-1 예외 3, 3-3 ②③, 1-4 역할 조정, 6-1·6-2·6-4는 구현으로 충실히 반영됐다.

다만 **High 3건**은 머지 전 수정을 권고한다. 셋 다 "드물지만 터지면 조용히 잘못되는" 유형이고, 그중 2건은 이 시스템이 스스로 가장 경계해 온 실패 형태(무기록 유실, fail-open 게이트)다.

## High — 머지 전 수정 권고

### H1. 실패 이벤트가 후속 커밋에 휩쓸려 영구 유실된다 (`ct2_orchestrator.py` main, 410~414행)

`handle_event` 예외 시 "커밋 보류 → 재기동 시 재처리"를 의도했지만, **confluent-kafka는 poll 후 인메모리 position이 전진**하므로 seek 없이는 같은 메시지가 다시 오지 않는다. 더 치명적인 것: `fdc.agent`는 다른 event_type도 흐르는 토픽이라, 실패한 ChamberRequalified(offset N) 직후의 타 이벤트(offset N+1)가 407~409행에서 **정상 커밋되며 N을 지나쳐** 버린다. 재기동해도 N은 재처리되지 않는다.

- pre-claim 실패(`_db()` 접속 실패 등)라면 `ct_decisions` 행조차 없어 **완전한 무기록 유실** — 헌법 7장 "실패 경로는 커밋하지 않고 seek 되감기" 자기 위반이며, WP-B1이 막으려던 바로 그 실패 형태다.
- **수정안**: 예외 시 해당 파티션을 실패 offset으로 되감고 backoff 후 재시도.

```python
except Exception as e:
    log.exception("handle_event 실패 — seek 되감기 후 재시도: %s", e)
    from confluent_kafka import TopicPartition
    c.seek(TopicPartition(msg.topic(), msg.partition(), msg.offset()))
    time.sleep(RETRY_BACKOFF_SEC)   # params.yaml 키로 (6-1)
```
(같은 이벤트 무한 재시도는 g2 선점 행이 있으면 skip-commit으로 자연 종결되고, pre-claim 실패는 DB 복구 시까지 되감기가 유지되어 유실이 없어진다.)

### H2. VAL 0장이면 게이트가 **조용히 PASS** — fail-open (`validate_bundle.py` validate, 380~453행)

사이드카 `val_wafers.json`의 `val`이 비어 있거나, 사이드카 유실 후 재유도 결과가 0장이면: A1·A2만 수행되고 `if val_wafers:` 가드에 걸려 **A3~A6·B·C·D 전 검사가 실행되지 않은 채 `gate_pass=True`**가 된다. 실행 검증으로 재현 확인했다 (`resolve_val_wafers` → `([], [], 'sidecar')`). 배포 결정의 단일 소스(3-3 ③)가 이 한 경로에서 fail-open이다. 정상 운영에선 run_ct2가 빈 val을 만들지 않지만, 게이트는 "정상 생산자 가정"이 아니라 자체로 닫혀 있어야 한다.

- **수정안** (3줄): VAL 해석 직후 빈 목록을 critical FAIL로 환원.

```python
if not val_wafers:
    checks.append(_c("A3_VAL_세트_해시", False,
                     "VAL 0장 — 사이드카/재유도 결과 빈 목록 (채점 불가 = 배포 불가)", critical=True))
```

### H3. 배포 후 감시가 현행 스키마에서 실행 불가 (`ct2_deploy_monitor.py` _fetch_window, 315~333행)

`db/init.sql` 정본과 이중 불일치: ① `wafer_predictions.ae_score` 컬럼이 없다 — AE 점수는 `anomaly_score`로 적재된다(consumer.py 380~401행에서 ae_score→anomaly_score 매핑 확인). ② `spc_violations`에는 `wafer_id` 컬럼 자체가 없다(alert 단위 테이블). 따라서 실행 즉시 UndefinedColumn → exit 1. docstring에 "스키마 결합 지점" TODO로 표시돼 있긴 하나, 이 모듈은 **`ct2_auto_promote` 개통 조건(3-3 ③ ⓓ)의 실증 대상**이라 미결이면 개통 자체가 막힌다.

- **수정안**: `p.anomaly_score` 사용 + SPC 플래그는 `wafer_predictions.spc_flags`(JSONB, 동일 행)로 판정하면 조인 없이 해결된다. `spc_violations`에 wafer_id를 추가하는 대안은 3-2에 따라 PM 승인 필요.
- 부가: `anomaly_score`에 **더미 폴백값**(consumer 388행)이 섞일 수 있으므로, 감시 창에서 더미 구간(AE 미탑재 기간)을 배제할 식별 조건도 함께 설계 필요 — 더미 위에서 분포 붕괴 판정은 무의미하다.

## Medium

### M1. exit code 2 충돌 — 설정 오타가 "게이트 FAIL/표본 미달"로 오진된다
argparse는 **인자 오류 시 exit 2**다. `ct2_validate_cmd` 템플릿에 오타가 나면 오케스트레이터 276행이 rc=2를 "게이트 FAIL"로 읽어 BLOCKED를 기록하고, 조립 스크립트 인자 오류(ap.error → exit 2)는 251행에서 "표본 게이트 미달(GATED)"로 기록된다. 번들명 검사에서 "오진 유발"을 경계한 것과 같은 계열의 함정. **수정안**: rc==2 처리 전에 산출물 실존 확인 — validate는 `report.exists()`(FAIL이어도 리포트는 반드시 쓰므로), 조립은 `[GATE]` 마커나 결과 파일. 부재 시 FAILED로 재분류.

### M2. 하드 크래시 시 RUNNING 영구 잔류 → 해당 Incident의 CT² 영영 미실행
retrain 최대 2시간 동안 프로세스가 kill/정전으로 죽으면 RUNNING 행이 남고, 재기동 후 재전달 이벤트는 g2에서 skip+commit된다. 이후 이 Incident의 CT²는 아무도 다시 열지 않는다(비종결 상태 잔류). 코드 주석은 "DB 확인 필요"로 인지하고 있으나 절차가 없다. **수정안**: `created_at`이 처리 상한(≈2.9h)을 넘긴 RUNNING을 FAILED('stale_claim')로 전이하는 스윕(기동 시 1회면 충분) 또는 런북 등재.

### M3. Windows에서 subprocess 출력 디코딩 (cp949)
`subprocess.run(capture_output=True, text=True)`는 로케일 인코딩으로 디코드한다. 자식 프로세스가 UTF-8 한글(파일 내용 포함 트레이스백 등)을 내면 UnicodeDecodeError가 **부모에서** 터져 전 단계가 "예외: ..."로 오진된다. 실운영이 Windows이므로 §7 cp949 교훈과 같은 계열. **수정안**: 4곳 모두 `encoding="utf-8", errors="replace"` (+자식 env `PYTHONUTF8=1`).

### M4. 자동 경로에서 CHANGELOG 기록 갭 (헌법 3-3)
"재학습 시 반드시 CHANGELOG 기록"인데, 현재 기록 주체는 promote(`ct2_deploy_approval`)·rollback(monitor)뿐이다. **BLOCKED/SHADOW/GATED로 끝난 재학습은 CHANGELOG에 남지 않고**, 수동 실행(retrain 378행)은 log.warning 리마인더뿐이다. `ct_decisions`엔 남으니 감사 공백은 아니지만 헌법 문구와는 어긋난다. **수정안**: run_ct2 완료 시(게이트 결과 무관) 오케스트레이터 또는 retrain이 CHANGELOG 1줄 append — monitor `_append_changelog` 패턴 재사용.

### M5. 단위 테스트 0건 — 배포 결정 단일 소스가 무테스트
`tests/`엔 `test_shap_contract.py`뿐. validate_bundle·monitor docstring이 "torch 없이 단위 테스트 가능" 구조를 명시했고 실제로 가능함을 이번 리뷰에서 실행으로 확인했지만, 정작 테스트가 없다. 게이트는 3-3 ③의 "항목 삭제·완화 PM 승인" 대상인데 회귀 테스트가 없으면 완화를 기계적으로 잡을 수 없다. **수정안**: 이번 리뷰 검증 케이스(어댑터 파싱실패/전멸, carve 경계 200→100/100·150→미분할, D2 뭉침·구조위반, 완화 감지 경고, cross_silence 유예·발화·길이가드, 붕괴 발화, H2 빈 VAL)를 그대로 pytest로 승격.

## Low

- **L1** `model.py` 189행 `torch.load`에 `weights_only=True` 명시 권장 — state_dict라 안전하며, torch<2.6 기본값(False)은 pickle 실행 경로, ≥2.6은 기본 변경으로 동작 차이 가능.
- **L2** `io_bundle.save_json`이 비원자 쓰기 — 신규 번들엔 무해하나 `make_drift`/`build-scorer`는 **기존 번들의 manifest를 제자리 덮어쓴다**. §7 원자 교체(tmp+`os.replace`) 패턴으로 통일 권장 (promote 신호는 이미 준수).
- **L3** monitor `--qual` 기본 0.2 하드코딩 — 정본은 배포 번들 `calib.json`의 `qual_threshold`. 재학습 후 앵커가 이동하면 침묵 판정이 어긋난다.
- **L4** `_render_cmd`의 `tpl.split()` — 경로 공백에 취약(현 리포 경로는 무공백). `shlex.split(tpl, posix=False)` 권장.
- **L5** `MIN_CALIB_FIT_WAFERS`(코드 100)와 `ct2_gate_min_val_wafers`(config 100) 이중 정의 — config만 올리면 "학습 통과·게이트 상시 FAIL" 조합 재발. retrain이 config 값을 읽게 하거나 최소한 양쪽 주석에 상호참조.
- **L6** 승인 상태 조회 케이싱 방식 불일치 — `guard_r9_approved`는 `IN ('Approved','APPROVED')`, approval 모듈은 `UPPER(status)=`. 쓰기는 전부 대문자로 확인됨(1-1 예외 3 준수). 읽기도 `UPPER(status)=`로 통일 권장.

## 리뷰 기준별 평가

**① 잘 작성되었는가 — 상.** 모듈 경계가 깨끗하고(순수 함수 분리로 torch-free 테스트 가능 — 실행으로 실증), 모든 비자명한 결정에 "왜"가 주석으로 남아 있으며, 실패 방향이 일관되게 fail-safe다(params 로드 실패→전 가드 잠금, converged 조회 불가→미생성, 깨진 calib→예외가 아닌 명시적 FAIL). 특히 홀드아웃 분리로 B군 항진명제를 제거한 것과 프로브를 결정적으로 설계한 것은 게이트의 신뢰성을 실질적으로 만든 핵심.

**② 버그 — 3건(High) + 오진 1건(M1).** H1(offset 유실)·H2(fail-open)·H3(스키마 불일치)은 실증/스키마 대조로 확정. 그 외 로직 버그는 발견하지 못했다. 데이터 누수(1-3) 관점: FORBIDDEN_INPUT 차단, C64 그룹 시간분할, scaler fit=TRAIN만, 게이트 홀드아웃의 학습·조기종료·calib 완전 미접촉 — 모두 확인, 위반 없음.

**③ 예외 처리 — 전반 우수, 누락 2계열.** poison 메시지 skip+커밋, `json.loads` 후 dict 가드, 역직렬화 실패 격리, graceful shutdown, claim 불변식("선점 후엔 어떤 실패든 terminal 기록"), 판정 강등 방지(D2가 잡은 계약 위반을 프로브 예외로 새지 않게 차단) 등 §6-2·§7 요구가 꼼꼼히 반영됐다. 누락은 H1의 실패 offset 처리와 M3의 디코딩 예외 정도.

**④ 성능 — 문제 없음.** 학습 규모(~2,000 wafer × 83피처)에서 full-batch 학습·프로브(σ그리드×채널×2 ≈ 120회 forward)·LedoitWolf 모두 수 초~수 분. subprocess 격리로 컨슈머 본선을 학습이 막지 않고, `max.poll.interval.ms`를 처리 상한+여유로 확대한 것(WP-B1)도 정확. 사소한 각주: 2시간 retrain의 stdout 전량 버퍼링(capture_output)은 로그량이 커지면 메모리를 먹으니 필요 시 파일 리다이렉트 고려.

## 종합 판정

**조건부 승인 (Request Changes)** — H1·H2·H3 수정 후 머지 권고. 세 건 모두 수정 규모가 작고(각 3~10줄 수준, H3만 스키마 협의 여지), 나머지 Medium은 후속 PR로 분리해도 무방하다. H2 수정과 M5(테스트 승격)는 같은 PR에 묶으면 회귀 방지까지 한 번에 끝난다. 참고: 본 파일들은 `src/agent_a_mlops/` 소유이므로 수정 PR은 **A 리뷰 필수**(3-1), H3에서 스키마 변경을 택할 경우 PM 승인(3-2).
