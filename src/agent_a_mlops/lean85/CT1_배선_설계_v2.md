## 0. 요지

루프 골격(오케스트레이터 → 자동 검증 게이트 → promote 신호 → 관리형 리로드 → 3중 기록)은 v1에서 확정·배선 완료됐다. v2의 본체는 하나다: **배포 후 상시 감시(WP-7/S3)를 폐지하고, 감시가 담당하던 결함 축 가운데 게이트·서빙 경로로 흡수 가능한 것만 확정 장치 2종으로 이관한다.**

- **D13 절대 열화 가드** — 상대 비교(C–C)가 원리적으로 못 잡는 "둘 다 나쁨"을 절대 상한으로 차단하고, 매일 공짜로 산출되는 champion 성능(`rmse_before`)의 연속 초과를 에스컬레이션한다.
- **D14 리로드 스모크** — 라벨 없이 즉시 보이는 유일한 신호(동작성)를 스왑 직전 1회 검사한다. 켜지는 모델과 답하는 모델은 다르다.

폐지의 근거 3축(일간 자기교정 + 팀 가정 + 커버리지 분해)과, 흡수되지 않고 남는 불가시 구간은 §5-3·§10에 정직하게 남긴다. **D13·D14는 폐지의 대가이므로, WP-9 구현 전 개통(S1)은 금지한다** (§9).

| **D14** | **리로드 스모크** ✅v2 확정 | consumer `_check_ct1_promote`가 **로드 성공 후·스왑 전** 최근 wafer 피처 링버퍼로 1회 예측해 ⓐ 전량 유한값 ⓑ 분산 > 0(상수 출력 차단) ⓒ 절대범위 이내를 확인. 실패 = **스왑 취소 + 신호 `failed/` + 기존 모델 유지 + ★로그**. 버퍼 미충전(기동 직후) 시 생략+경고(차단 아님 — 교착 방지). **게이트가 아니라 서빙 보호(헌법 6-2)의 확장**이다 — 정확도 판정 없음·라벨 무관·validation.json 불요 → 개정 ④(consumer 게이트 한정)와 모순 없고, 게이트 이전 모델(초기 champion)로의 수동 신호·롤백도 막지 않는다 | 게이트는 조립 CSV 축에서 라벨로 채점한다 — **서빙 스트림 축의 즉시 결함**(전량 NaN·상수 출력·로드는 되나 응답 병리)은 라벨 도착 전까지 어떤 게이트도 못 본다. 라벨 없이 즉시 판정되는 유일한 축. 비용 = 승격일 1회·수십 wafer 예측(수십 ms) |

### 3-1. 실행 기준시각 (개정 ① — 2026-08-05 PM 확정)

- 정기 = **오전 7시 KST = naive UTC 전일 22:00** (`ct1_run_at_utc: "22:00"`, 구 제안 02:00 대체). 엔지니어 출근 직전 최신 모델이 서빙에 올라 있게 하는 배치다.
- ct_id·`last_scheduled_day`의 날짜축은 UTC — **KST 아침 실행분의 날짜가 전일자로 찍힌다.** 불변식은 "UTC 날짜당 정기 1회"이고, 표시 계층에서만 KST 변환한다(헌법 6-4의 표시층 원칙 동형).
- 캐치업 2단(코드 이행 완료): ⓐ 같은 (UTC)날 지각 기동 — 실행 시각 경과면 즉시 1회. ⓑ 24시간 초과 밀림(마지막 정기 실행일 ≤ 전전일) — 시각 무관 즉시 1회. 정기 실행이 FAILED·LOCKED로 끝나면 **그날을 소비하지 않는다**(리뷰 S2 — 일시 장애 1번이 하루치를 삼키지 않게).
  - **단서 (v2.1, 2026-08-07 코드리뷰 H2 — §6 `ct1_max_daily_failures`)**: 당일 **연속 FAILED**가 상한(기본 3)에 도달하면 그날을 **소비한다** + ★에스컬레이션 1건. 결정론적 실패(데이터 glob 오경로·스키마 불일치·코드 결함)의 재시도 폭주가 `ct_decisions`를 오염시키고 원인 로그를 묻어버리기 때문이다. 익일 정기가 자연 재시도하므로 영구 정지가 아니다. `LOCKED`는 세지 않는다(실패가 아님) — 즉 위 문장은 **`LOCKED`에 대해서는 무조건, `FAILED`에 대해서는 상한 내에서** 성립한다.

## 4. 상세 설계

### 4-1 ~ 4-4. 오케스트레이터·창 절단·조립·게이트 (v1 승계 — 코드 이행 완료)

v1 §4-1~4-4 그대로다. 요지만: 오케스트레이터는 상주(`--once` 지원)·멱등(ct_id RUNNING 원자 선점, `INSERT … RETURNING`)·subprocess 격리·graceful shutdown. 창 절단·레짐 확장은 `lean85_pipeline.slice_train_window()` 단일 소스, 누수 가드 2종은 명시적 `raise`(헌법 7장 — `assert` 금지). 조립기는 표본 게이트를 **쓰기 전에** 판정하고 산출물은 gzip. 게이트 4군(A 완결성 / B 누수·창 — B2b 학습∩평가 독립 검증 포함 / C 표본 / D 승격판정)에 **v2가 D군 항목 1건(D13)을 추가**한다 — §4-7.

### 4-5. promote · 리로드 · 롤백 (D5 — v2 개정)

- 신호: `control/ct1/promote_<ct_id>.json` = `{ct_id, model_dir(절대경로), model_version, rollback, promoted_at}` — tmp + `os.replace` 원자 교체. 자동·수동(차단기 강하 구간)·롤백이 **같은 채널** → consumer 단일 구현.
- consumer: 스캔 주기마다 **최신 신호만** 적용(구 신호 superseded 보관 — 롤백이 큐잉된 구 promote에 즉시 뒤집히는 문제 차단, 리뷰 S10). 적용 순서 = **로드 성공 → D14 스모크 통과 → 원자 스왑** (v2 — §4-8). 실패는 `failed/` 이동 + 기존 유지, 성공은 `processed/` 이동.
  - **구현 확인 (2026-08-07 리뷰 F1 — 초기 배선은 이 문단을 이행하지 않았다)**: 구 구현은 `sorted(glob)[0]`(이름 사전순)을 스캔당 1건 적용했고, `-rollback` 접미의 `-`(0x2D)가 `.json` 의 `.`(0x2E)보다 앞서 **롤백이 먼저 적용된 뒤 다음 스캔에서 큐잉된 구 promote 가 그것을 뒤집었다**(하네스 실측 적용 순서 `['good_model', 'bad_model']`). 자동 롤백을 폐지한 v2 체제에서 수동 롤백은 유일한 복구 수단이므로 필수 결함으로 처리했다. 현행: 정렬 키 = **payload `promoted_at`(aware UTC) → 동률 시 rollback 우선(F9 — 아래) → 파일 mtime → 파일명**(`consumer._signal_sort_key`), 선택 = `max()`, 미적용분은 **적용 시도보다 먼저** `superseded/` 로 이동한다(적용 도중 사망해도 구 신호가 되살아나지 않게).
  - **가드의 정본은 파일 이동이 아니라 적용 워터마크다 (2026-08-07 리뷰 후속)**: `_move_signal` 은 이동 실패를 삼키므로(Windows 파일 잠금·권한·디스크 — 헌법 7장 등재 계열), 이동에만 기대면 **보관에 실패한 구 신호가 다음 스캔의 유일한 후보가 되어 적용된다** — 최신분은 이미 `processed/` 로 빠졌으므로 `max` 가 그것을 집는다. 고치려던 S10 이 좁게 재발하는 경로다(실측 재현 `['good_model', 'bad_model']`). 현행: consumer 가 **마지막으로 선택된 신호의 시각**(`_ct1_signal_watermark`)을 들고, 그 이하의 신호는 두 번 다시 적용하지 않는다. 워터마크는 **적용 성공 여부와 무관하게 선택 시점에** 갱신한다 — 선택 자체가 "이 시각 이하는 전부 대체됐다"는 선언이고, 신 신호가 스모크에서 떨어졌다고 구 신호가 되살아나면 안 되기 때문이다. 프로세스 재기동 시 소실되며 그때는 `champion.json` 부트스트랩이 기준이다(수용).
  - **동률 시 롤백 우선 (F9 — 2026-08-07 재리뷰 정정)**: `promoted_at` 은 1초, mtime 은 커널 틱(수 ms) 해상도라 **연속 드롭이 같은 키를 받는 동률이 실측**됐고(ext4 연속 `write_text` 동률 재현 — 통제 실험 A·B 모두 구 promote 승), 그때 이름 타이브레이크는 `….json`(0x2E) > `…-rollback.json`(0x2D) 이라 **항상 롤백이 진다.** 정렬 키 2번째 요소로 `rollback` 플래그를 넣어 동률에서 롤백이 이기게 한다 — 롤백은 사람의 복구 개입이고, 시간으로 구분 불가능한 동률에서 구(불량) promote 에 지면 안 된다. rb 는 mtime **앞**이다(같은 초 안의 순서 판정을 신뢰도 낮은 mtime 에 맡기지 않는다). 시각이 다르면 여전히 최신 승(통제 실험 C — rb 가 진짜 시간 순서를 뒤집지 않는다). 워터마크(`key[0]`)는 ts 그대로라 무영향. 이 결함은 수정안 v1(F1)의 키 설계가 지정한 것을 충실히 구현한 결과다 — 구현이 아니라 설계 잘못(수정안 §12 증보 참조). 회귀 = `test_rollback_wins_timestamp_ties`(RED 확인 후 수정).
  - 신호 디렉토리의 종말 상태는 3종이다: `processed/`(적용 성공) · `failed/`(적용 시도 실패) · `superseded/`(적용 없이 대체됨 — **감사 보관, 삭제 없음**). 앞 둘은 "이 ct_id 를 어떻게 처리했나"의 결과라 재드롭 시 최신이 덮는 게 맞지만(`replace`), **`superseded/` 는 "그때 큐에 무엇이 있었나"의 증거라 덮어쓰지 않는다** — 같은 ct_id 재드롭은 수동 경로의 정상 시나리오이고, 덮으면 앞 기록이 소리 없이 사라진다. 충돌 시 mtime 접미를 붙여 병존시킨다(`_move_signal(keep_existing=True)`). 보관 자체가 실패하면 ★error 로 드러내되 흐름은 막지 않는다 — 재적용은 워터마크가 이미 막고 있다.
  - CT²(`_check_ct2_promote`)는 §8-E가 순서 보존을 규정하므로 **대칭을 의도적으로 끊는다** (S10 형태가 CT² 롤백에도 성립하는지는 CT² 설계 리뷰 안건).
  - 회귀: `tests/test_ct1_wp9_guards.py::TestS10LatestSignalOnly` 6건.
- **개정 ④ (consumer 게이트 한정)**: consumer는 promote 신호를 신뢰하며 validation.json을 재검하지 않는다 — 신호를 드롭하는 경로가 오케스트레이터의 게이트 PASS 이후 한 곳뿐이라는 불변식이 근거다. D14는 이 원칙과 충돌하지 않는다: 스모크는 모델 품질 판정이 아니라 **동작성 확인**(서빙 보호)이고, 게이트 이전 모델·리포트 없는 폴더로의 수동 신호도 막지 않는다.
- 롤백: **자동 롤백은 도입하지 않는다** (개정 ③ — WP-7 폐지). 롤백 = 직전 champion(D8이 무조건 보존)으로 promote 신호 **수동 재드롭** + `ct_decisions(ROLLED_BACK)` + CHANGELOG. 롤백 신호도 같은 채널이므로 D14 스모크가 동일 적용된다.
- **수동 경로의 실행 주체 = CLI (F4 — 2026-08-07 PR-2 신설)**. 위 두 줄(수동 승격·롤백)은 그동안 **절차만 있고 코드가 없었다**: 신호 드롭 함수는 있었지만 `champion.json` **포인터 갱신 주체가 어디에도 없었다.** 사람이 신호만 드롭하고 포인터를 두고 가면 ⓐ 다음 게이트가 **서빙 중이 아닌 모델**과 비교하고(헌법 3-3 ①) ⓑ D13 streak 의 champion 이름 변화 리셋(§8-1 ①ⓑ)이 발화하지 않으며 ⓒ `ct_decisions(ROLLED_BACK)` 기록이 수작업 SQL 에 의존한다. 셋 다 급할 때 사람이 잊는 후속 작업이라 하나로 묶는다.

  - 순서는 자동 경로(`_do_promote`)와 같다: **RUNNING 선점 → 신호 → 포인터 → 기록**(`finalize_decision` + CHANGELOG + `fdc.mlops`). 부분 실패가 "기록은 승격인데 배포는 안 됨"(S12 위반 방향)이 아니라 "배포됐는데 기록 실패" 쪽으로 떨어지게 한 것이고, 포인터 실패는 §4-8 과 같은 극성으로 `trigger_reason/ptr_fail` + ★로그 + **별도 종료 코드**(`EXIT_MANUAL_PARTIAL`=4)로 드러낸다 — 0 을 주면 사람이 후속 복구를 놓치고, 1 을 주면 "안 됐구나" 하고 신호를 한 번 더 드롭한다.
  - 감사 상태는 `PROMOTED` / `ROLLED_BACK`. 전자는 D8 GC 의 보존 쿼리(`IN ('PROMOTED','AUTO_PROMOTED')`)가 이미 인지하는 값이고, 후자의 대상(직전 champion)은 포인터 `model_dir` 로 keep 된다 — **GC 안전**.
  - **★게이트 가드 (2026-08-08, PM 리뷰 #123)**: 승격 대상은 **게이트 PASS 인 그 번들**이어야 한다 — ⓐ `validation.json` 실재 ⓑ `gate_verdict == "PASS"`(SKIP 도 거부 — 미검증 항목이 있다는 뜻) ⓒ `bundle_name == 폴더명`(다른 번들의 PASS 리포트 복사로 우회 차단 — 헌법 1-1 예외 3 ⓑ 와 같은 취지). 위반은 종료 코드가 아니라 **`ValueError`** 다: 폴더 오타(manifest 부재)는 사용자가 경로를 잘못 짚은 것이지만 이쪽은 **헌법 3-3 ① 을 뚫는 시도**이고, 종료 코드는 스크립트의 `|| true` 한 줄에 삼켜지는 반면 예외는 스택과 함께 남는다(헌법 7장 "가드를 `assert` 로 작성 금지"와 같은 취지). 선점·신호 **앞**에 둔다 — 뒤에 두면 감사 축에 RUNNING 만 남기고 죽어 F7 리퍼가 치워야 한다. **롤백은 면제** — 대상이 *이미 champion 이었던* 모델이고 v2(개정 ③)에서 수동 롤백은 유일한 복구 수단이라, PASS 를 요구하면 게이트 도입 이전 champion 으로 되돌아갈 수 없어 사고 대응 수단이 가드에 막힌다. *(그동안 `manifest.json` 존재만 확인해 `FAIL`=BLOCKED stamp 를 지정해도 그대로 배포됐다 — 하필 이 경로가 차단기 강하 구간에 사람이 stamp 를 손으로 타이핑하는 자리다.)*
    - **`--rollback` 은 면제한다**: 직전 champion 은 **승격 시점에 이미 PASS 였고**, 부트스트랩 champion(게이트 이전 모델 — 현 `lean85_20260720_163040_initial`)은 `validation.json` 자체가 없다. 자동 롤백을 폐지한 v2(개정 ③)에서 **유일한 복구 수단**을 게이트 산출물 유무로 막으면 장치의 목적이 사라진다. 개정 ④("게이트 이전 모델·리포트 없는 폴더로의 수동 신호도 막지 않는다")와도 이 선에서 정합한다 — 막는 것은 **앞으로 세우는 승격**뿐이고, 되돌리는 경로는 열려 있다. 게이트 이전 모델을 앞으로 세우려면 `--rollback` 이거나 게이트 1회 통과가 전제다.

### 4-7. D13 — 절대 열화 가드 (v2 신설 확정)

**무엇을 막나**: D4(C–C)는 상대 비교다. champion과 challenger가 **같은 결함**(오염된 학습 원천·라벨 왜곡·조립 경로 버그)을 공유하면 gain < 3% → SKIP → 결함 champion 유지로 수렴하고, 상대 지표는 끝까지 침묵한다. AE 라벨 오염 38장 사고가 정확히 이 형태였다(재학습·게이트·PM 보고 전부 통과 — 헌법 7장 등재).

**설계**:

- **게이트 항목(승격 판정)**: challenger `rmse_after`(온셋 제외 pooled) ≤ `BENCH_POOLED(99.84) × ct1_gate_abs_rmse_max_ratio`. 초과 시 상대 개선율과 무관하게 skip_reasons 추가 → **SKIP**(champion 유지 — critical FAIL 아님: 누수·계약 위반이 아니라 품질 미달이므로 FAIL/SKIP 분리 원칙을 지킨다).
- **champion 대조(에스컬레이션)**: 게이트가 매 실행 산출하는 `rmse_before`를 같은 상한과 대조해 리포트에 기재. 오케스트레이터가 연속 초과 streak를 상태 파일에 유지, `ct1_abs_guard_champion_streak`(제안 3) 도달 시 ★에스컬레이션 + **차단기 회귀 검토 신호**(§5 후속의무 3′의 관측 수단 ⓐ). **경보만이다** — 게이트 우회 강제 교체 금지(D10 동형).
- **단일값 발화 금지(연속 조건인 이유)**: H=1일 평가 표본의 pooled RMSE는 일 변동성이 크다 — 어려운 wafer 몇 장이 건강한 모델의 하루 수치를 밀 수 있다. 상한은 여유 있게, 발화는 연속으로.
- **앵커 선택 근거**: `BENCH_POOLED 99.84`는 모든 stamp의 manifest에 실리는 확정 벤치(시간축·재학습 전제)다. 일간 평가 실측(D1 pooled 54.80)과 무재학습 발산(334.24) 사이에 놓여 "정상 변동"과 "붕괴"의 판별 앵커로 적합하다. 배수·streak 수치는 **본 문서 미기재**(D12) — 단일 소스는 `validate_lean85.DEFAULTS` + `ct.ct1_gate_*`, 확정은 WP-8 리허설 스윕.

**한계(정직)**: 절대 상한 **안쪽**의 미세 오염은 여전히 불가시다 — AE 오염 사례는 지표상 정상으로 보이는 오염이었다. D13이 잡는 것은 "붕괴"이지 "왜곡"이 아니다(§10-8).

### 4-8. D14 — 리로드 스모크 (v2 신설 확정)

**무엇을 막나**: 현행 스왑 조건은 "로드 성공"뿐이다(`Lean85Predictor.__init__` = 로드 + 피처 85 대조). 로드는 되는데 응답이 병리적인 모델 — 전량 NaN·상수 출력·범위 이탈 — 은 그대로 서빙에 오르고, 그 결함이 라벨 축(게이트·익일 재평가)에 잡히려면 **최소 하루**다. 스모크는 라벨 없이 즉시 판정되는 유일한 축(동작성)을 닫는다. 주로 잡는 결함: 직렬화 손상, consumer 환경 격차(xgboost 버전 등 — 게이트는 오케스트레이터 환경에서 채점했다), 로드는 성공하나 forward가 병리적인 경우.

**설계**:

- **위치**: `_check_ct1_promote` — 로드 성공 직후·스왑 전. 승격·수동·롤백 신호 공통(같은 채널 단일 구현).
- **입력**: consumer가 유지하는 최근 완성 wafer **피처 링버퍼**(`ct1_smoke_buffer_wafers`, 제안 50) — `predict_wafer`가 이미 빌드한 table 행을 재사용한다(추가 피처 빌드 없음 = 서빙 부하 0).
- **판정 3종**: ⓐ 예측 전량 유한값(`np.isfinite`) ⓑ 표준편차 > 0(상수 출력 = 부스터 손상 신호) ⓒ 절대범위 이내(기본값은 `validate_lean85.DEFAULTS`에 학습 타깃 분포 기반으로 정의 — 수치 미기재, D12).
- **실패**: 스왑 취소 + 신호 `failed/` + 기존 모델 유지 + ★에러 로그. **서빙 보호가 배포보다 우선**(헌법 6-2)의 확장이다.
- **버퍼 미충전**(기동 직후·표본 < `ct1_smoke_min_wafers`, 제안 20): **생략 + 경고**(차단 아님) — 재기동 직후의 promote가 영구 교착되는 것을 막는다. 기동 부트스트랩 로드(`_resolve_model_dir` 경유)는 스모크 대상 아님(신호 경로 한정 — 부트스트랩은 더미 폴백이 기존 안전망).
- **감사 정합의 한계(명시)**: 오케스트레이터는 신호 드롭 시점에 이미 `AUTO_PROMOTED` 기록·champion 포인터 갱신·CHANGELOG를 마쳤다. 스모크 실패 시 **감사는 승격인데 서빙은 구모델**인 불일치가 생긴다 — `failed/` 신호 + ★로그가 그 사실의 실체이고, 정합 복구는 사람이 한다(재승격 또는 포인터 원복 재드롭). consumer→DB 역기입은 도입하지 않는다(consumer DB 무의존 유지 — §10-9). 이 불일치는 v1의 로드 실패 경로에도 동일하게 존재했던 것으로, v2는 새로 만든 게 아니라 **명시**한 것이다.
- **역방향 불일치의 차단 (2026-08-07 리뷰 F3)**: 위 불일치의 **반대 극성**(서빙은 신모델인데 감사는 FAILED)은 허용하지 않는다. `drop_promote_signal` 이 성공한 순간부터 '배포됨'은 사실이므로, 그 뒤의 `set_champion`·`append_changelog` 실패로 상태를 FAILED 로 뒤집으면 champion 포인터가 낡은 채 다음 게이트가 엉뚱한 비교를 한다. 배포 시퀀스를 `ct1_orchestrator._do_promote()` 로 묶어 **신호 드롭 이후의 실패는 상태를 `AUTO_PROMOTED` 로 유지**하고 detail·★로그로 수동 복구를 지시한다. 신호 드롭 **자체**의 실패는 미배포이므로 그대로 전파(FAILED)한다. 회귀: `test_do_promote_survives_pointer_failure` · `test_do_promote_signal_failure_propagates`.
  - **부분 실패는 감사 축에도 올린다 (2026-08-07 리뷰 후속)**: `detail` 은 `ct_decisions` 에도 `fdc.mlops` 에도 실리지 않아 로그 한 줄이 유일한 증거였다 — 그러면 "서빙=신모델 / 포인터=구모델"인 건이 감사 테이블상 **완전 정상인 `AUTO_PROMOTED`** 로 보이고, 다음 실행의 `champion_dir()` 은 낡은 포인터를 정본으로 읽어 **서빙 중이 아닌 모델**과 challenger 를 비교한다(헌법 3-3 ① 비교 기준점 붕괴). 파생으로 D13 의 champion 이름 변화 리셋(§8-1 ①ⓑ)도 발화하지 않는다. 현행: `_do_promote` 가 in-memory report 에 경고를 얹고(`PROMOTE_WARN_KEY` — **게이트 리포트 필드가 아니다**, validation.json 에 쓰이지 않는다) `handle_trigger` 가 `trigger_reason` 접미로 승격시킨다 → `daily_sliding/auto_promoted/ptr_fail`(36자 < 64). `WHERE trigger_reason LIKE '%ptr_fail%'` 로 조회 가능. 선례 = 미배포 후보명 접미(S12)·CT² `/reaped`. `fdc.mlops` 는 무변경이다 — 필드 추가는 소비자 리뷰 대상이고(헌법 2-2) 감사 정본은 `ct_decisions` 다. 회귀: `test_pointer_failure_lands_in_audit_reason`.

양안 비교표는 v1 §5 참조(이력). v1 ①안의 핵심 리스크 "게이트가 못 거르는 결함이 무인 배포"에 대한 대응이 v1은 WP-7(감시·롤백) 선행 권고였고, **v2는 그 권고를 폐지하고 D13·D14 + 아래 후속의무로 대체**한다.

### 5-2. ①안 후속의무 (v2 개정 — 구 1·2·3 대체)

1′. **(구 1 "S3/WP-7 선행 권고" 폐지 — 개정 ②③)** 안전망은 다음 표로 재구성한다. WP-7 폐지의 대가가 D13·D14이므로 **WP-9 구현 전 S1 개통 금지**(§9).

| 결함 축 | 담당 장치 |
|---|---|
| 상대 열화 (challenger가 champion보다 못함) | 게이트 D군 C–C (D4) |
| 절대 붕괴 · "둘 다 나쁨" | **D13** (challenger 상한 = 승격 차단 / champion streak = 에스컬레이션) |
| 서빙 즉시 결함 (NaN·상수·응답 병리·환경 격차) | **D14** + "로드 성공 시에만 스왑" |
| 잘못된 승격의 지속 | 일간 재평가 — 단 노출 상한은 "다음 실행"이 아니라 **"다음 승격"까지**다(§5-3 ⓐ) |
| 사고 시 정지 | 차단기 `ct1_auto_promote: false` 수동 강하 (PASS → SHADOW 기록만) |
| 사후 추적 | 3중 기록 (`ct_decisions` · CHANGELOG · `fdc.mlops`) |

2′. **(구 2 유지)** 차단기의 의미 — `false`는 개통 절차가 아니라 **사고 시 회귀 스위치**다. 내리면 PASS가 SHADOW로 기록만 되고 교체는 사람이 신호 드롭으로 수행한다(같은 채널이라 consumer 무변경).

3′. **(구 3 개정 — 관측 수단 명시)** 미탐 1건 회귀 규율: "배포된 모델의 결함이 게이트·스모크를 통과했다"가 확인되면 **즉시 차단기 강하 + 원인 규명 전 재전환 금지 + WP-7 재소환 검토**(폐지는 팀 가정 위에 서 있다 — 가정이 반증되면 폐지도 재검토한다). 관측 수단(감시 프로세스가 없으므로 명시가 의무다): ⓐ **D13 champion 가드 연속 발화** ⓑ **시뮬 정답지 대조 회귀 실측**(Scorecard 유형 프로브 — 배포 모델의 예측 결함 확인) ⓒ **수동 발견**(엔지니어·리허설). 어느 경로든 동일 규율.

### 5-3. 감시(WP-7/S3) 폐지 근거와 커버리지 분해 (개정 ③ — 신설)

**근거 3축**:

ⓐ **일간 캐던스의 자기교정** — 매일 라벨 축 재평가가 돌므로 잘못된 승격은 익일 게이트에서 상대·절대 양축으로 재측정된다. **단 정직하게: 노출 상한은 "다음 실행"이 아니라 "다음 승격"까지다.** 승격 임계 3.0%는 실증 개선폭(이음새 제외 +3.87%)과 근접해 다수 일이 SKIP일 수 있고(§10-1 미검증 승계), `ct1_max_stale_champion_days: 7` 경보의 존재 자체가 연속 미승격을 정상 시나리오로 상정한다. 결함 champion이 하루가 아니라 일주일 앉아 있는 경로가 설계에 이미 있다 — 이 구멍을 메우는 것이 **D13 champion streak**다(교체가 아니라 발화 — 사람이 개입할 근거를 만든다).

ⓑ **팀 가정 (2026-08-05)**: 배포 전 게이트 검증 정확도 = 100%. 반증 장치 = 후속의무 3′(미탐 1건 회귀 + WP-7 재소환 검토). 가정은 공짜가 아니라 **회귀 규율로 담보된 가정**이다.

ⓒ **커버리지 분해** — 감시가 담당하던 축을 분해하면: 라벨 기반 성능 축은 게이트 D군·D13이 **같은 데이터로** 매일 흡수한다(상시 프로세스가 주는 추가 정보는 라벨 지연 하에서 일간 배치 대비 크지 않다). 라벨 무관 즉시 축은 D14가 스왑 시점에 흡수한다. 남는 것은 아래 "흡수 불가" 3종이며, 이는 상시 감시로도 잡기 어려운 축이다(감시 역시 라벨·임계 기반이므로).

**흡수 불가로 남는 구간 (한계 — §10-8 등재)**: ⓐ 라벨 도착 전의 "그럴싸한 오답"(동작은 정상, 값은 오염 — 스모크는 동작성만 본다) ⓑ 절대 상한 안쪽의 미세 오염(AE 사례는 지표상 정상으로 보였다) ⓒ 학습-서빙 skew(게이트는 조립 CSV 축, 서빙은 Kafka 스트림 축 — 스모크는 스트림 축의 동작성만 확인하고 값 일치는 확인하지 않는다).

**CT²와의 비대칭 정당화**: CT²는 배포 수개월 1회·비지도(라벨 없음)·미탐이 물리 판정(Qual·스크랩)에 직결이라 배포 후 감시·자동 롤백이 개통 조건이다(헌법 3-3③ⓓⓔ). CT①은 배포 일간·지도 학습(라벨 도착)·매일 재평가 — 상시 감시의 한계 효용이 낮다. **헌법 3-3③은 명문상 CT² 전용**이라 CT①을 구속하지 않는다(v1 §5 논거 승계 — 위헌 아님, 헌법 개정 불요).

## 6. config 신설·정리 (`config/params.yaml` `ct:` 절)

현행 `ct1_*` 키(v1 §6 + 명령 템플릿 3종·`ct1_data_glob`·`ct1_now_override`)는 유지. **v2 신설 4키 — `config/params.yaml` 반영 완료(2026-08-05, WP-9 ⓓ)**. 값은 여전히 제안치이며 확정은 WP-8 스윕 + 합의안 증보:

```yaml
ct:
  # --- D13 절대 열화 가드 (단일 소스 validate_lean85.DEFAULTS — 여기서 override) ---
  ct1_gate_abs_rmse_max_ratio: 1.5   # 상한 = BENCH_POOLED(99.84) × ratio. 일간 실측 54.8과
                                     #   발산 334.2 사이 판별 앵커 — WP-8 스윕 대상
  ct1_abs_guard_champion_streak: 3   # champion 연속 초과 에스컬레이션 (단일값 발화 금지 —
                                     #   H=1일 pooled RMSE 는 일 변동성이 크다)
  # --- D14 리로드 스모크 (consumer — params.yaml 정본, 헌법 6-4) ---
  ct1_smoke_buffer_wafers: 50        # 최근 wafer 피처 링버퍼 크기 (predict_wafer 산출 재사용)
  ct1_smoke_min_wafers: 20           # 미달 시 스모크 생략+경고 (기동 직후 교착 방지)
  # --- v2.1 신설 1키 (2026-08-07 코드리뷰 H2) ---
  ct1_max_daily_failures: 3          # 당일 연속 FAILED 상한 — 도달 시 그날 소비 + ★에스컬레이션
```

**v2.1 신설 (2026-08-07 — 코드리뷰 H2 반영)**: `ct1_max_daily_failures`. 기존 규율은 "`FAILED`·`LOCKED` 면 그날을 소비하지 않고 backoff 후 재시도"였는데(§3 루프 · 리뷰 S2), **일시 장애와 결정론적 실패를 구분하지 않는다**. 데이터 glob 오경로·스키마 불일치·재학습 코드 결함처럼 fast-fail 하는 원인이면 하루 수백 회 재시도가 되고, 매 시도가 새 SEQ 의 `ct_decisions` 행(RUNNING→FAILED)과 subprocess 를 남겨 **감사 테이블 오염 + CPU 낭비 + 진짜 원인 로그가 홍수에 묻힘**으로 끝난다. 그래서 당일 **연속** FAILED 가 상한에 도달하면 오늘을 소비하고 ★에스컬레이션 1건으로 종결한다 — 익일 정기가 자연 재시도하므로 영구 정지가 아니며, D10(노화 경보)·0표본 경보와 같은 "루프는 조용해지고 사람이 볼 신호를 남긴다" 규율이다. **`LOCKED` 는 세지 않는다** (다른 프로세스가 도는 중 = 실패 아님 — 현행 유지). 구현 = `ct1_orchestrator.after_scheduled` · 회귀 테스트 = `tests/test_ct1_failure_cap.py`.

스모크 절대범위 ⓒ의 기본값은 config 키를 늘리지 않고 `validate_lean85.DEFAULTS`에 둔다(키 남발 방지 — 필요 시 후속 추가) — `smoke_pred_min/max`로 반영 완료(근거 §8-1 ⑤). ~~**주석 정정 의무(WP-9 동시)**~~ **이행 완료**: `ct1_auto_promote` 주석의 v1 문구("S2 개통 전에 WP-7을 올리거나…")를 v2 문구("WP-9 구현 + WP-8 리허설 + §7-3 ④ PM 확인 선행, §9")로 교체했고, `params.yaml` 헤더·`lean85_pipeline`·`ct1_orchestrator`·`validate_lean85`의 "설계 v1" 참조도 v2로 현행화했다.

| ① | **champion 교체 시 streak 처리** | ⓐ `AUTO_PROMOTED` 면 **이번 관측을 세지 않고** 0 리셋 ⓑ **champion 이름 변화**로도 리셋(단 이 경우는 리포트가 이미 새 champion 이므로 이번 관측부터 1) | 이 지표는 "지금 서빙 중인 champion 이 연속 초과했다"는 뜻이다. 리셋하지 않으면 **교체된 옛 champion 의 이력으로 새 champion 을 고발**한다. ⓑ가 필요한 이유: 차단기 강하 구간의 **수동 승격·수동 롤백**도 champion 을 갈아치우는데 그때 status 는 `SHADOW` 라 ⓐ에 안 걸린다(§4-5 — 자동·수동·롤백은 같은 채널). 승격 실행의 리포트는 **교체 직전** champion 의 관측이므로 세면 안 되고, 이름 변화는 **이미 새** champion 의 관측이므로 세야 한다 — 두 경우가 다르다 |
| ② | **측정 불가(`champion_over_cap=null`) 처리** | streak **유지**(증가도 리셋도 안 함) | champion 부재·표본 미달은 champion 이 건강하다는 증거가 아니다. 리셋하면 격일 표본 미달만으로 연속이 영원히 끊겨 **가드가 조용히 죽고**, 증가시키면 없는 증거로 발화한다 |
| ③ | **streak 임계의 코드 폴백** | `ABS_GUARD_STREAK_DEFAULT = 3` (config 와 동일) | `ct1_auto_promote` 계열의 "로드 실패 = 전 가드 잠금" 규율과 **방향이 반대**다. 이 값은 가드를 여는 스위치가 아니라 **경보를 늦추는 값**이라, 잠금(=∞)으로 두면 params 로드 실패 시 경보가 사라진다 |
| ④ | **D14 ⓑ(분산>0)의 전제** | 링버퍼 **입력이 서로 다를 때만** 적용 (동일하면 검사 생략 + 기재) | 입력 85-벡터가 전부 같으면 건강한 모델도 상수를 낸다. 그대로 두면 저트래픽·리플레이 구간에서 **오탐으로 배포가 막히는 교착**이 된다 — 스모크는 배포 보호이지 배포 차단기가 아니다 |
| ⑤ | **D14 ⓒ 절대범위 수치** | `smoke_pred_min/max = 100 / 5000` (`validate_lean85.DEFAULTS`) | 학습 타깃 C65 실측 지지구간(`synthetic_1y` 80,294 wafer: min 481.2 · p0.1 526.6 · p99.9 1592.0 · max 1678.0)에 넉넉한 여유. **정확도가 아니라 동작성 판정**이므로 느슨한 게 맞다 — 여기 걸리는 건 0·음수·폭주지 "조금 빗나간 예측"이 아니다 |

| ⑥ | **스모크가 태우는 예측 경로** | `model.predict`(sklearn)가 **아니라** `booster.predict(pred_contribs=True)` 의 합 — `Lean85Predictor.predict_batch()` 신설 | 서빙이 발행하는 값이 그 합이다(`predict_wafer`). §4-8이 지목한 결함 1순위가 "게이트는 오케스트레이터 환경에서 채점했는데 consumer 의 xgboost 가 다르다"인데, 그 격차는 정확히 **`pred_contribs` 계약이 깨지는 형태**로 나타난다. 다른 API 로 검사하면 그 경로를 한 번도 안 태우고 통과시킨다 — 유일한 방어인 `_verify_contrib_identity` 는 **스왑 후** 첫 wafer에 돌고 로그만 남긴 채 그 값을 발행한다 |
| ⑦ | **streak 의 축** | **UTC 일(day)** — 같은 날 2회차는 세지 않음 | 정기(일간)와 요란 PM 이벤트가 겹치면 거의 같은 평가창으로 두 번 돈다. §4-7의 연속 조건 근거가 "H=1일 pooled RMSE 의 **일** 변동성"이므로 축도 일이어야 한다 — 아니면 상관된 증거 2건으로 임계에 도달한다. **비대칭 명문화 (2026-08-07 리뷰, F5)**: 같은 날 2회차의 `over=True` 는 세지 않으나 **`over=False` 는 리셋한다** — 그날의 판정을 최신 관측으로 갱신하는 것이며, 경보를 **늦추는** 방향이라 안전측이다. 같은 날의 정상 관측은 "champion 이 지속 붕괴 상태는 아니다"라는 실증거다. 대안(같은 날 2회차는 over 값 무관 유지)은 축 일관성은 좋으나 회복 증거를 버려 채택하지 않았다. 회귀 고정 = `test_champion_streak_same_day_recovery_resets` |

부수 방어 2건:

## 10. 잔여 확인·정직한 한계

1. **실증의 조건부성** (v1 승계) — 일간 우위 +22.66%는 이음새 포함, 제외 시 +3.87%. 승격 임계 3.0%와 근접 — 승격 빈도·flapping은 WP-8에서 H·임계 스윕으로 확인. 게이트 판정은 사후 소급 시뮬로만 검증됐고 운영 프로토콜(D4)로는 미실측.
2. **라벨 지연 미검증** (승계) — 시뮬은 즉시 라벨 전제. 실운영 계측 지연이 H·평가 표본·**D13 대조 시점**에 미치는 영향 미측정.
3. **데이터 원천 이원화** (승계) — 실운영 전환(raw 적재기 + `wafer_predictions` 조인)은 후속(D9).
4. **다챔버 전역 PM** (승계 — ADR-0001) — 단일 전역 모델 전제 유지.
5. **CT²와의 자원 충돌** (승계) — 요란 Incident 직후 CT²(최대 2.5h)와 CT① 일간 실행 중첩 가능. 공유 락 미설계 — 저빈도라 후속.
6. **같은 날 2번째 요란 PM 미감지** (승계 — 계약 §8-B-1 단서 ②) — 일간 정기가 익일 흡수, 수용.
7. **D4 공정성 전제** (승계) — 초기 champion(`lean85_20260720_163040_initial`)은 H 버퍼 규율 이전 모델 — 첫 비교들은 유불리 혼재 가능(게이트 B4가 경고로 기재, 리허설 확인).
8. **감시 폐지의 잔여 불가시 구간 (v2 신규 — §5-3)** — ⓐ 라벨 전 "그럴싸한 오답"(스모크는 동작성만) ⓑ 절대 상한 안쪽의 미세 오염(D13은 붕괴를 잡지 왜곡을 잡지 못한다) ⓒ 학습-서빙 skew(게이트 CSV 축 vs 서빙 스트림 축). 반증 장치 = 후속의무 3′(미탐 1건 회귀 + WP-7 재소환 검토).
9. **스모크 실패 시 감사-서빙 불일치 (v2 신규 — §4-8)** — AUTO_PROMOTED 기록·포인터 갱신 후 consumer 스모크 실패 시 서빙은 구모델. `failed/` + ★로그가 실체, 정합 복구는 수동. v1 로드 실패 경로에도 동일하게 존재하던 것을 명시한 것.
10. **D13 표본 한계 (v2 신규)** — H=1일 pooled RMSE의 일 변동성 때문에 상한은 여유·발화는 연속 조건. 배수(제안 1.5)·streak(제안 3)는 리허설 확정 전 잠정치.
12. **D13 cap 이 감사에 영속화되지 않는다 (2026-08-05 WP-9 리뷰 신규)** — `abs_rmse_cap`·`champion_over_cap` 은 게이트 리포트(`validation.json`)와 로그에만 남고 `ct_decisions`·`fdc.mlops` 에는 없다. `rmse_before` 는 저장되므로 형식상 도출은 가능하지만, 도출에 필요한 cap 이 **WP-8 스윕에서 바뀔 config 값**이라 스윕 이후 과거 실행을 DB만으로 재판정할 수 없다. 해소는 계약 §7 페이로드 확장(필드 추가 = 소비자 리뷰 필요, 헌법 2-2)이므로 WP-6 잔여 PR에 합류시킨다.
13. **헌법 정합 자체 점검 (v2 개정)**: 3-3③ⓓⓔ는 명문상 CT² 전용 — CT① 감시 의무 없음, WP-7 폐지는 위헌 아님(§5-3) · D13 = 게이트 항목 추가(강화 — PM 승인 불요, 삭제·완화 시 PM 승인) · D14 = 서빙 보호(6-2) 확장, 게이트 아님(개정 ④ 정합) · 1-1(승인 불요 경로 — 물리 조치 아님) · 1-2(무관 — 독립 캐던스) · 1-3(누수 가드 raise 2종 + B2b 독립 검증 + C64 그룹 분할) · 3-3(캐던스·게이트 선행·기록) · 4-1(stamp 신규 저장·GC 해석 확정) · 4-3(WP-6 동시 PR) · 6-1/6-2/6-4 · 7장(assert 금지·원자 교체·32자·NaN 금지·상태 확인 가드).
