## 3. 트리거 · 경계

- **상류 (범위 밖)** — PM의 승인 결정은 `approval_records`(D/PM 소유, P4-1)에 기록되거나 `fdc.correction` 이벤트로 흐른다. B5-1a는 그 결과로 **승인된 `correction_id` 하나**를 입력으로 받는다.
- **B5-1a 책임** — 그 `correction_id`의 PROPOSED 재설정을 `control_limits`에 적용 + 이력 상태 전이. **그게 전부.**
- **승인자·승인시각**(approver / decided_at)은 `approval_records`가 이미 보유 → B5-1a가 다시 기록하지 않는다.
- **트랜잭션 경계 = 호출자 소유** (recalc_writer 패턴 계승 — 자체 commit 안 함).

## 4. 처리 흐름 — `apply_approved(conn, correction_id) -> None`

```
1. SELECT PROPOSED 행   ─ correction_id + status='PROPOSED' 가드, FOR UPDATE
      └ 없음 → 멱등 no-op (이미 적용됐거나 없는 id) → 로그 후 return
2. SELECT 현행 control_limits (is_active) ─ group_key로, FOR UPDATE (lock=True)  (method·k_sigma·q_low·q_high 승계)
      └ None → correction이 아직 PROPOSED면 동시 교체 의심 → 스텝2 재조회 (최대 N회 — §동시성 ①)
              재조회로도 활성행 부재 → 경고 후 return (진짜 그룹 관리선 부재 = 이상 상태)
3. NULL 가드 ─ center_after/ucl_after/lcl_after 중 NULL이면 경고 후 return (control_limits는 NOT NULL — §6)
4. sigma 역산  (§6)
5. new_version = f"v{n}"  (n = _NEXT_VERSION 스칼라 — 내부에서 이미 MAX+1, 추가 +1 금지; **'v' 접두 필수** — §버전 문자열)  [_NEXT_VERSION 재사용]
6. DEACTIVATE 현행 (is_active=false)                     [_DEACTIVATE  재사용]  ┐ 쓰기 순서
7. INSERT 신규 버전 (is_active=true)                     [_INSERT_LIMIT 재사용]  ┘ 불변식 (L2)
8. UPDATE limit_corrections
      SET status='APPROVED_APPLIED', limit_version_after=new_version   (← 같은 f"v{n}")
      WHERE correction_id=:cid AND status='PROPOSED'    [신규 SQL]
```

**멱등성** — 1·8의 `status='PROPOSED'` 가드로 두 번 호출돼도 두 번째는 0행 매칭 → 관리선 불변.

**버전 문자열 포맷 (필수)** — `_NEXT_VERSION`은 **정수 스칼라**(예: `6`)를 돌려준다. `'v'` 접두 부착(`new_version = f"v{n}"`)은 `apply_auto`(`recalc_writer.py:157`) 본문에만 있고 **재사용하는 SQL 상수엔 없다.** 접두 없이 맨정수(`'7'`)로 저장하면 다음 채번의 `SUBSTRING(limit_version FROM 2)` → `CAST('' AS INTEGER)`가 **그 그룹 전체에서 예외로 멈춘다**(그룹 단위 마비, 실측 확인). `control_limits.limit_version`과 `limit_corrections.limit_version_after`는 **동일한 `f"v{n}"` 문자열**을 공유해야 `correction_history._SELECT_BY_VERSION`(정확일치 조회)도 맞는다.

**버전 번호 재계산** — `limit_corrections.limit_version_before`(제안 시점 값)에 의존하지 않고 매번 현행 `MAX+1`을 재계산한다. 단 이는 **버전 번호만** 안전하다는 뜻 — 값·선행버전 기록은 아래 Staleness 참조.

**동시성 (락=안전성, 유실=재시도)** — 스텝2의 FOR UPDATE는 **버전 중복 INSERT(유일성 위반)를 실제로 막는다.** 다만 메커니즘은 "순차 재채번"이 아니다 — 같은 그룹에 두 승인이 겹치면, 패자는 READ COMMITTED 스냅샷 때문에 승자가 갈아끼운 새 활성행을 못 보고 **0행(None)**을 받는다(실측 확인). 이때 그냥 return하면 **승인이 조용히 유실**(correction은 PROPOSED로 방치)되므로, 스텝2는 **correction이 아직 PROPOSED면 재조회(최대 N회)해 새 활성행 위에 재적용**한다(① 경량 자기복구). 이 재시도는 D0(승인 수기·직렬)에서 충분하며, 근본 처리(충돌 재시도/SERIALIZABLE)는 라이브 배선(B5-1)에서 확정한다(④ — §8).

**Staleness (버전 번호 외)** — 제안(v5 기준)과 승인 사이 정기재산정이 v6를 auto-apply하면, B5-1a는 현행(v6)의 method·k_sigma는 승계하되 center/ucl/lcl은 **제안 시점 v5 값**을 v7로 적용한다 → v6가 반영한 신정보 **퇴행** + `limit_version_before='v5'`가 실제 선행 v6와 불일치(감사 이력 어긋남). **단 판정 엔진은 delta_sigma 합산이 아니라 reset_ref 텔레스코핑(`recalc_engine.py:153`)을 쓰므로 판정 자체는 오염되지 않는다** — 손해는 값 퇴행 + 이력 불일치까지다. 재검증 정책은 승인 게이트(B5-1) 소관으로 이월(§8).

## 6. sigma 역산 규칙

`limit_corrections`에 `sigma_after` 컬럼이 없으므로 밴드에서 역산한다.

- **sigma 그룹** — `sigma = (ucl_after − center_after) / k_sigma`  (대칭 밴드 → 정확값)
- **quantile 그룹 (KEEP\*)** — `control_limits.sigma`는 참고 통계(판정 미사용)이고 `k_sigma` 컬럼이 NULL이므로, **현행 행의 sigma를 승계**한다. 판정에 안 쓰이므로 값 선택이 결과에 영향 없음.
- **NULL 안전 (sigma 한정)** — 승계하는 현행 sigma는 스키마상 `control_limits.sigma FLOAT NOT NULL`이라 항상 존재한다(§4 스텝2에서 현행 행 부재는 걸러짐). 따라서 **sigma에는** 별도 NULL fallback 불필요. ⚠️ 단 이 안전은 **sigma 승계에만** 해당 — correction에서 그대로 읽는 `center_after/ucl_after/lcl_after`는 `limit_corrections`에서 NULL 허용이므로 별도 가드가 필요하다(§4 스텝3, §5).

> `recalc_engine.sigma_ref_of` 헬퍼와 동일 철학 — 판정 자(尺)는 quantile이면 밴드 역산, sigma면 컬럼. 여기선 **저장만** 하므로 quantile은 승계로 단순화한다. (밴드 역산 `(ucl_after − lcl_after)/(2·k_sigma)`로 통일하려면 quantile은 `k_sigma` 컬럼이 NULL이라 config 상수를 끌어와야 하는데, 판정 미사용 필드에 config 의존을 더할 값어치가 없다.)

## 8. 범위 밖 · 향후 작업

**지금 범위 밖**

- Kafka `fdc.correction` 구독 / 라이브 배선 → B5-1 라이브 수급과 함께 (D0 의존)
- 거부(`REJECTED`) 전이 → B5-1 / PM 승인 게이트
- **승인자·승인시각 기록 → `approval_records` (D/PM).** ⚠️ `approval_records`엔 `correction_id` 컬럼이 없어(`init.sql:242`) correction 단위 승인 조회가 지금은 불가 — **라이브 배선 시 approver 게이트 필수**(현재 B5-1a는 `status='PROPOSED'`만 신뢰).
- 제안↔승인 사이 현행이 바뀐 경우의 staleness 정책(스테일 제안 재검증) → 승인 게이트(B5-1) 소관. B5-1a는 승인된 값을 그대로 적용한다(§4 Staleness).
- **동시 승인 충돌 근본 처리** — B5-1a는 ① 재조회 재시도로 D0를 방어하나, 다중 승인·자동재산정이 실제로 겹치는 라이브에서는 충돌 재시도(또는 호출자 트랜잭션 SERIALIZABLE)를 정책으로 확정 → B5-1 배선(§4 동시성 ④).

**향후 작업 — ⑤ B안(공용 헬퍼 추출)으로 승격**

현재는 A안(`recalc_writer` SQL 상수 import, B4-3 무수정)으로 **최소 변경**한다. 이유는 B4-3가 이미 테스트 통과한 **닫힌 태스크**이고, 지금 로컬 트리·git이 **손상 복구 중**이라 리팩터를 안전하게 검증할 수 없기 때문이다. 아래 조건이 갖춰지면 B안으로 정석화한다.

1. 로컬 손상 복구 완료 + B4-3를 안전하게 재오픈할 수 있게 될 때, **또는**
2. 관리선 삽입 SQL이 실제로 바뀌어 A안의 "내부 상수 빌려쓰기" 결합이 유지보수 마찰이 될 때

→ 그 시점에 `recalc_writer`와 `approval_apply`가 공유하는 **공용 헬퍼**(예: `_apply_new_version(conn, group_key, center, sigma, ucl, lcl, …)`)를 추출하고, `apply_auto`·`apply_approved`가 함께 호출하도록 정리한다. **기능 회귀 없이 구조만 정돈하는 리팩터**이므로, 안정화 이후 별도 커밋으로 진행한다.

## 10. 테스트 계획

- **happy path** — PROPOSED 1건 승인 → 신규 버전 `is_active=true`, 기존 `false`, correction `status=APPROVED_APPLIED`, `limit_version_after` 채워짐. **center·ucl·lcl 정확값 assert**(ⓒ 의미 교체 방어 — `_INSERT_LIMIT` 컬럼 전치 등)
- **버전 문자열 포맷** — 적용 후 `limit_version`이 `f"v{n}"`(접두 有), 같은 그룹 재적용 시 `_NEXT_VERSION` 정상 채번(맨정수 회귀 없음)
- **멱등성** — 같은 `correction_id` 2회 호출 → 2번째 no-op (관리선·버전 불변)
- **없는 correction_id / 이미 APPROVED_APPLIED / REJECTED** — no-op, 예외 없음
- **NULL 가드** — `center_after` NULL인 PROPOSED → 경고+return, `control_limits` 미변경 (not-null 위반 크래시 방지)
- **현행 행 부재** — 재조회로도 활성행 없음 → 경고+return, `control_limits` 미변경
- **sigma 그룹 역산** — `sigma == (ucl_after − center_after) / k_sigma`
- **quantile 그룹** — `q_low`·`q_high`·`sigma` 승계, 판정 미사용
- **쓰기 순서 불변식** — 부분 유니크(그룹당 active 1개) 위반 없음
- **동시성 (통합 레벨)** — 같은 그룹 동시 적용 → 승자 vN 적용, 패자는 재조회로 vN+1 재적용(유실 없음), 버전 유일성 위반 없음 (행 락은 단위테스트 어려우니 통합 테스트로)

## 11. 불변식 (헌법 정합)

- **4-1 버전 보존** — 덮어쓰기 금지, 기존 행은 `is_active=false`로만 물러남
- **3-2 스키마 무변경** — 신규 컬럼 없이 기존 스키마로 (sigma 역산으로 해결)
- **그룹당 `is_active` 1개** (부분 유니크) — DEACTIVATE→INSERT 순서로 보장
- **버전 충돌 차단 + 유실 방지** — 현행 is_active 행 FOR UPDATE로 버전 중복 INSERT를 막고(안전성), 동시 교체 시 패자는 재조회로 재적용해 승인 유실을 막는다(§4 동시성)
- **버전 문자열 규약** — `limit_version`·`limit_version_after`는 항상 `f"v{n}"`(정수 앞 'v' 접두) — 접두 누락 시 `_NEXT_VERSION` 채번 크래시
- **원자성** — commit은 호출자 소유 (한 트랜잭션에서 관리선 교체 + 상태 전이가 함께 성공/실패)
