## 1. 배경 · 목적

**수정 승인**은 설계 확정 개념이다 (기획서 v4.3+): "현업 엔지니어는 승인/거절만 하지 않는다 — **제안값을 수정해서 승인**한다('+4.1%는 과하고 +3.0%로'). 원안+수정값 모두 `approval_records`에 기록." 이 "AI 원안 vs 엔지니어 보정" 차이가 최고 품질의 학습 데이터가 된다.

**경로**: `POST /incidents/{id}/decision {action: modify, modified_value}` → LangGraph `Command(resume)` → **`fdc.correction`(CorrectionApplied) 발행 → B가 한계 즉시 갱신** (계약 §241-242).

**빈틈(=PM이 짚은 것)**: 현재 `apply_approved`는 `limit_corrections`의 `center_after/ucl_after/lcl_after`를 **PROPOSED 그대로** 적용하고 σ는 밴드에서 역산한다. → **① 엔지니어 수정값이 이 경로에 반영되는 방법**과 **② 센터 수정 시 밴드 재산출**이 정의돼 있지 않다.

---

## 2. 현황 · 왜 규칙이 필요한가 (근거)

`apply_approved`(`approval_apply.py:64`)는:
- PROPOSED 행의 `center_after / ucl_after / lcl_after`를 읽어 `control_limits`에 그대로 write.
- σ는 **밴드에서 역산**: `_reverse_sigma` = `(ucl_after − center_after) / k_sigma` (sigma 그룹) / `current.sigma` 승계 (분위수 그룹) — `approval_apply.py:53-61`. (`limit_corrections`엔 `sigma_after` 컬럼이 없어 밴드가 유일한 σ 출처)

**문제**: 엔지니어가 **센터만** 고치고 밴드를 안 고치면 — 예: 센터 100→103인데 ucl/lcl은 옛 100 기준(106/94) — 
- σ 역산 왜곡: `(106−103)/3 = 1` (실제 σ=2인데 1로),
- 밴드 비대칭: `ucl−center = 3`, `center−lcl = 9`.
→ **깨진 관리선이 control_limits에 들어가고 Nelson 판정이 오염된다.** 이 방지가 본 규칙의 목적.

## 4. 필드 규칙 상세

> 공통 원칙: **원안(`*_after`)은 절대 불변. 수정값은 항상 `*_modified`(nullable)에.** 각 값은 apply 시 **`COALESCE(수정값, 원안)`** — 수정값 있으면 그것, NULL이면 원안. 전부 NULL이면 = 일반 승인(원안 그대로). **modify와 일반 승인이 한 경로로 통일된다.**

### 4-1. sigma 그룹 — 센터 수정 → 밴드 재산출

수정 대상 = **센터만**(`center_modified`, 절대값 하나). 밴드폭(σ) 직접 수정은 현 범위 밖 — 센터를 옮기고 밴드는 σ로 따라간다.

```
제안:  center_after=100, ucl_after=106, lcl_after=94   (k=3, σ=2)
수정:  center_modified=103
apply: σ    = (ucl_after − center_after)/k = (106−100)/3 = 2   # 원안서 복원(불변이라 가능)
       ucl  = 103 + 3·2 = 109
       lcl  = 103 − 3·2 = 97
       → control_limits: center=103, sigma=2, ucl=109, lcl=97   # 대칭 유지 ✅
```

`center_modified` NULL이면 = 일반 승인(center_after 그대로, 밴드 재산출 없음).

### 4-2. 분위수 그룹(KEEP*) — 경계 직접 수정

분위수 그룹은 `ucl/lcl = 분위수 컷`이고 `center±kσ` 밴드가 없다(σ는 판정 미사용 참고 통계). 센터 재산출이 무의미 → **ucl/lcl을 직접 수정**한다.

```
제안:  center_after=28, ucl_after=50, lcl_after=10   (σ 승계)
수정:  ucl_modified=55   (상한만; lcl_modified=NULL)
apply: ucl = COALESCE(55, 50) = 55        # 수정값
       lcl = COALESCE(NULL, 10) = 10      # 원안 그대로(부분 수정)
       center=28 승계, σ 승계             # 재산출 없음
```

**부분 수정 지원**: 상한만/하한만/둘 다 — 고친 것만 채우면 됨(COALESCE).

## 5. 가드 · 감사 (결정 5 상세)

### 5-1. Layer 1 — apply 구조 가드 (B가 차단)

해소된 최종값 기준으로 검사:
- **공통 (양 method 통일 — PM 2026-07-24)**: center/ucl/lcl **not-None·finite**(None·NaN·inf 아님 — 원안 `*_after` NULL은 **σ 계산 전 프리체크→APPLY_FAILED**) + **`ucl ≥ center ≥ lcl` 강제 검사**. sigma·분위수 구분 없이 동일 적용 — sigma는 `center±kσ`라 정상값이면 자동 만족하지만 명시 검사로 엣지까지 차단, 분위수는 직접 입력의 뒤집힘·center 이탈 방어. *(기존 "sigma 자동보장 / 분위수 ucl>lcl+center 권장" 분기 → **단일 강제 검사로 통일**)*
- **sigma 추가**: 복원 `σ > 0` (원안 σ=0 퇴화 차단) + **현행 `k_sigma` not-None·`>0`**(σ 복원 나눗셈의 분모 — NULL/0이면 `/None`·`/0` raise→rollback→무한 재전달이라 §5-3 fail-closed 원칙대로 σ 계산 **전** 프리체크→`APPLY_FAILED`). *(리뷰 반영 2026-07-24 — NULL 프리체크가 `*_after`만 막던 구멍)*
- **finite는 σ도 포함**: 분위수 승계 `σ`도 `isfinite` 검사(오염 행 NaN σ의 무검증 write 차단).
- **FP 슬랙**: 비교는 `EPS=1e-9` 허용(`ucl−center ≥ −EPS`) — 부동소수 미세오차 방어. (sigma 계산 밴드는 반올림이 순서 보존이라 오탐 사실상 없으나, 분위수 independent 값·미래 대비 방어 관례)

### 5-2. 크기(magnitude) 정책 상한 없음

수정값 **크기는 엔지니어 권한**이다(HITL — 헌법 1-1). incident 재수립이 이미 "무상한·항상 승인"이고 그 위의 modify도 동일. B는 "너무 크다"고 되돌리지 않는다. → **구조(순서·finite·σ>0)만 검사, 크기 정책은 미검사.** (10배 오타 확인 등은 프론트 UX 권고사항)

### 5-3. 실패 처리 — 조용히 죽지 않게

구조 위반 = **영구 불량 입력**(재전달해도 동일 실패). Kafka at-least-once에서 두 나쁜 결말을 동시에 피한다:
- **무한루프**(예외→커밋 안 함→영원히 재전달·재실패) ❌
- **조용한 유실**(삼키고 skip→엔지니어는 승인했는데 미적용·아무도 모름) ❌

**해법**: `control_limits` **미기록** + `limit_corrections.status='APPLY_FAILED'`(값만, 스키마 무변) + **ERROR 로그(위반 항목·center/ucl/lcl/σ 값 상술** — 엔지니어 원인 파악) + **정상 `return`**(★ raise 금지). → 호출자 `_handle_correction`의 `with engine.begin()`가 **APPLY_FAILED를 커밋**하고 오프셋도 커밋(재시도 X = 루프 방지). **raise하면 rollback→상태 유실+무한루프**(=조용한 실패)이므로 절대 금지. transient DB오류만 raise(=rollback+재시도). → 대시보드가 APPLY_FAILED 노출→엔지니어 재입력. (기존 "correction_id 부재 → skip+커밋" 패턴과 일관)

**재처리 규약 (PM 확정 2026-07-24)**: APPLY_FAILED 후 엔지니어 재입력 시 — **오케스트레이터가 `*_modified` 갱신 + `status`를 `PROPOSED`로 되돌리고 `fdc.correction` 재발행**. B는 재발행된 correction을 받아 `apply_approved` 재실행 → `WHERE status='PROPOSED'`라 갱신된 행(새 `*_modified`)을 다시 읽어 재검증·적용(통과=`APPROVED_APPLIED` / 재실패=다시 `APPLY_FAILED`, 루프). **B 코드 추가 변경 없음**(이미 PROPOSED+`*_modified` read). 상태 전이 소유 — `APPLY_FAILED→PROPOSED`·재발행=**오케스트레이터** / `PROPOSED→APPROVED_APPLIED`·`→APPLY_FAILED`=**B**.

### 5-4. Layer 2 — 사후 품질 (별개 층)

구조를 통과해 **정상 적용된** 값의 품질(엔지니어 판단이 나쁠 수 있음)은 사후 감시가 잡는다:
- **재수립(Phase 2) 경우**: `verify_forward`(firm 후 forward **N=30장** 오탐율 채점) → 너무 빡빡하면 FAIL/reopen.
- **일반 재산정 경우**: 라이브 SPC 모니터링(Nelson 지속) — 나쁜 값이면 알람 패턴 이상.
- 구조 오류는 Layer 1에서 이미 차단돼 wafer까지 오지 않으므로, Layer 2는 "구조 정상·품질 의심" 값만 본다.

### 5-5. 감사 추적

- `limit_corrections`: **원안(`*_after`) + 수정(`*_modified`) 병존** → "AI 원안 vs 엔지니어 보정" 학습 자산.
- `approval_records`(PM): 원안+수정값+누가·언제·사유 (기획서 — **PM 워크플로가 기록**, B는 미기록).
- 체인: `approval_records`(결정) → `limit_corrections`(correction_id·원안·수정) → `control_limits`(적용 버전). B 몫 = status 전이 + 버전 write.

## 6. apply 의사코드 (개정안)

```python
from src.agent_b_spc.tttm_engine import EPS    # 1e-9 공유 상수 재사용(인라인 금지 — 6-1)

def apply_approved(conn, cid) -> bool:          # ★② 반환: 적용됨(True) / 미적용(False, APPLY_FAILED·skip)
    p = SELECT center_after, ucl_after, lcl_after,
               center_modified, ucl_modified, lcl_modified,   # ★ 신설 3
               calc_window_n, trigger_type
        FROM limit_corrections WHERE correction_id=cid AND status='PROPOSED' FOR UPDATE
    if p is None: return False                 # 멱등(없음/이미 처리) → 호출자 후속 skip
    cur = current_active(group)                # method, k_sigma, q_low/high, sigma

    # ★① NULL 프리체크 (기존 approval_apply:89-92 유지) — 원안 *_after는 σ 복원·COALESCE 폴백 소스라 필수.
    #    반드시 σ 계산·isfinite 전에(None 산술=TypeError→except→무한루프 방지).
    if p.center_after is None or p.ucl_after is None or p.lcl_after is None:
        UPDATE limit_corrections SET status='APPLY_FAILED'
            WHERE correction_id=cid AND status='PROPOSED'          # ★④ status 가드
        logger.error("원안 *_after NULL → APPLY_FAILED: cid=%s", cid)
        return False

    if cur.method == 'sigma':
        center = coalesce(p.center_modified, p.center_after)
        sigma  = (p.ucl_after - p.center_after) / cur.k_sigma      # 원안서 복원(불변)
        ucl, lcl = center + cur.k_sigma*sigma, center - cur.k_sigma*sigma
        extra_ok = sigma > 0                                       # sigma 전용
    else:  # quantile
        center, sigma = p.center_after, cur.sigma                  # 승계
        ucl = coalesce(p.ucl_modified, p.ucl_after)
        lcl = coalesce(p.lcl_modified, p.lcl_after)
        extra_ok = True
    # 5-1 통일 가드(PM): 양 method 공통 — finite + ucl≥center≥lcl (FP 슬랙 EPS=1e-9 재사용)
    ok = isfinite(center, ucl, lcl) and (ucl - center >= -EPS) and (center - lcl >= -EPS) and extra_ok

    if not ok:                                                     # 5-3
        UPDATE limit_corrections SET status='APPLY_FAILED'
            WHERE correction_id=cid AND status='PROPOSED'          # ★④ status 가드
        logger.error("가드 실패 → APPLY_FAILED: cid=%s method=%s center=%.6g ucl=%.6g lcl=%.6g sigma=%.6g "
                     "(ucl≥center≥lcl·σ>0 중 위반)", cid, cur.method, center, ucl, lcl, sigma)
        return False   # ★ 정상 return(raise 금지) → 호출자 `with engine.begin()`가 APPLY_FAILED 커밋.
                       #   raise 시 rollback→상태 유실+무한루프. transient DB오류만 raise=재시도.

    DEACTIVATE(group); INSERT control_limits(center, sigma, ucl, lcl, method, ...new version)
    UPDATE limit_corrections SET status='APPROVED_APPLIED', limit_version_after=ver
    return True    # ★② 적용됨 → 호출자가 reload + firm 후속 진행
```

## 7. B 코드 변경 범위 (구현 시)

## 8. 확정 스키마·계약 (PM dev 반영 2026-07-24)

- **`limit_corrections` +3 nullable 컬럼**: `center_modified` · `ucl_modified` · `lcl_modified` (FLOAT, 수정 승인 시만 채움 / NULL=일반 승인). 원안 `*_after`는 불변.
- **`status='APPLY_FAILED'`** 값 채택 (스키마 무변, 대시보드 노출).
- **순서 보장 = 기입→판정→발행 (fail-closed)**: 오케스트레이터가 `*_modified` 기입 → 구조 판정 통과 시에만 `fdc.correction` 발행 (실패=미발행=안전). **write-before-publish**라 B는 correction 수신 시 `*_modified`가 항상 채워짐 = 레이스 없음. (B §5-1 가드는 최후 방어로 유지 — defense in depth)
- **재입력 재처리**: APPLY_FAILED → 오케스트레이터 `*_modified` 갱신·`PROPOSED` 복귀·재발행 → B 자동 재시도 (§5-3).
- **`modified_value`는 절대값으로 해소**해 컬럼 기입 · **method별 컬럼 라우팅**(sigma=`center_modified`만 / 분위수=`ucl_modified`·`lcl_modified`만) — B는 method 보고 해당 컬럼만 소비(sigma는 ucl/lcl_modified 조용히 무시). B는 해석 없이 밴드만 재산출.
